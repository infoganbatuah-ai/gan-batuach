## Minimum data need versus effective privilege

One comparison needs exactly one active `LEGACY_HMAC` row for its pinned enrollment, selecting only `id`, `gateway_id`, `observer_site_id`, `tenant_id`, `deployment_profile`, `config_version`, `status`, `lifecycle_state`, `identity_scheme`, and `refresh_token_hash`. Only the local comparator may see the verifier in process memory; it must never appear in a Product/API response, audit, exception, telemetry or log.

The required Production **read capability is not yet available under an approved least-privilege identity**. The previous proposed direct database LOGIN and verifier-returning function were withdrawn; the pending migration is an explicit no-op. The connected Production catalog was inspected read-only on 2026-10-21: `public` grants `USAGE` to `PUBLIC`, all 57 audited public functions are `PUBLIC EXECUTE`, the enrollment table has RLS with `is_admin()`, and `service_role` bypasses RLS and can read more than these two rows. A new `NOINHERIT`/`NOLOGIN` role cannot subtract `PUBLIC` rights. An existing `service_role` key in a new broker would **not** be least privilege merely because application SQL is pinned. There is no approved private Product-side broker or credential transport; Vercel requires a Production deployment and its ordinary function routes are network-reachable, so it is not silently an acceptable private execution host.

### Two reviewable paths, neither activated

1. **Preferred if an existing private broker is approved:** run the existing JavaScript comparator in a protected Product-side process with a bound two-row read capability and an authenticated, private, one-time credential channel from the Home Keychain. No new DB LOGIN is created, so no new direct LOGIN inherits unrelated `PUBLIC EXECUTE`. The Product-side broker still requires a security review of its *effective* DB identity; use of existing `service_role` is a broader privilege risk that needs explicit acceptance or further isolation. No such private host/channel is presently verified. A public Vercel route or exposed Supabase RPC is not an acceptable substitute. Production deployment, authenticated TLS/destination verification, ephemeral memory-only secret handling, cost and rollback would require separate approval.
2. **Host-local restricted DB connection, alternative only:** keep the local credential in Keychain and deliver only the exact verifier to the signed local process over a private TLS database connection. This would require a dedicated restricted LOGIN, an unexposed private fixed-row read object, network/TLS controls and a global `REVOKE USAGE ON SCHEMA public FROM PUBLIC` *before* login activation. Otherwise the new LOGIN can execute unrelated PUBLIC-granted functions. That schema revoke affects Supabase-managed roles currently relying on PUBLIC USAGE (`authenticator`, `dashboard_user`, `cli_login_postgres`, `supabase_auth_admin`, `supabase_etl_admin`, `supabase_read_only_user`, `supabase_realtime_admin`, `supabase_replication_admin`, `supabase_storage_admin`, and others); their compatibility and exact compensating grants are **not proven**. The private DB response also crosses a verifier trust boundary and requires explicit security approval. Do not deploy this alternative from the current PR.

There is no third path that both reuses the existing JavaScript comparator and keeps *both* inputs in their separate locations: either the Keychain credential moves to a trusted Product process or the Production verifier moves to a trusted Home process. This unavoidable crossing must be selected and approved explicitly. A database-side new hash comparator would be a parallel engine and is out of scope.
