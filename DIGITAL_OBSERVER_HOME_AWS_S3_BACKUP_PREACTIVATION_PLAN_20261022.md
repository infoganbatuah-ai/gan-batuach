## Proposed private bucket and trust boundary — not deployed

1. After separate approval, create one **general-purpose** bucket in `il-central-1` with a unique project backup-only name, Object Ownership `Bucket owner enforced` (ACLs disabled), all four Block Public Access controls, no website hosting, no public ACL/policy/link, and a bucket policy denying requests where `aws:SecureTransport=false`. Verify effective public-access analysis. Do not use the OTA/release bucket or its signing keys. [AWS S3 security baseline](https://docs.aws.amazon.com/AmazonS3/latest/userguide/security-best-practices.html).
2. Default SSE-S3 is the initial no-new-KMS-key at-rest layer. For restricted payloads add a vetted authenticated **client-side envelope encryption** tool, with a new backup-specific recovery secret held in approved owner-controlled custody and a separately sealed recovery copy; verify decryption on an isolated sample before any upload. Do **not** reuse or export Home Keychain credentials. If the client-encryption tool, recovery key or lawful processing approval is unavailable, stop. A customer-managed symmetric KMS key would be a separate cost/security decision; current Ed25519 signing keys stay untouched. [AWS S3 default encryption](https://docs.aws.amazon.com/AmazonS3/latest/userguide/bucket-encryption.html), [AWS KMS pricing](https://aws.amazon.com/kms/pricing/).
3. Use short-lived project-owned federated credentials if available. A dedicated backup writer gets only bucket location/list restricted to its named backup prefix, multipart-list/abort needed for recovery, and object write to that prefix. A separately approved restore identity gets list/read only; no wildcard account access, no `s3:*`, no signing KMS permission, no long-lived key in files or Git. Deny deletion for the writer. Exact IAM policy, principal trust and credentials must be reviewed after the account administrator confirms the available federation path; no role or login was created.
4. Enable versioning, but make the first campaign **manual and one-shot**. Use immutable run-ID prefixes so an overwrite cannot silently replace a prior backup. Set no automatic current-version deletion before a complete restore and retention/legal-hold review. A later lifecycle may retain one current and one previous approved generation with a minimum 30-day noncurrent grace period; do not apply that deletion policy as part of first upload. Record lifecycle cost and evidence. Versioning alone does not cap spend or prove restore. [AWS versioning/lifecycle](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html).
5. Create a backup-specific AWS Budget **only after approval** with alerts around 70/85/95% of the approved incremental allocation, plus an application-side preflight and stop when total selected encrypted bytes, object/part count or expected retained versions exceed the limits below. AWS Budgets is an alert, **not a hard spending cap**; charges can exceed an alert before notification. No scheduled uploader is proposed. [AWS budget behavior](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html).

## Capture, verification and rollback sequence for the later approved run

**Pre-write stop gate:** verify account/region/least-privilege session; exact named bucket security and cost controls; legal classification; complete unique-data manifest; measured encrypted output and object count; local source and independent restore capacity; recovery key custody; and current all-in ₪15/active-paying-user forecast from the restricted supplier ledger. Neither AWS CLI, a vetted client-encryption utility nor host `pg_dump` is currently available on the Mac PATH; use reviewed versions and the existing isolated PostgreSQL tooling only after approval. Do not copy raw DB files from a running VM.

1. Freeze only the **isolated Development** writers for a bounded window after owner coordination; do not touch Production or installed Home services. Verify the local Supabase identity and Postgres version. Take a transaction-consistent logical database dump, including Auth and migration history, and a separate roles/extensions/config inventory. Capture private Storage object bytes and metadata at the same logical cutoff, or record the inconsistency window and rerun. Supabase documents that database backups contain Storage metadata **but not object bytes**. [Supabase backup contract](https://supabase.com/docs/guides/platform/backups).
2. Inventory local Git deltas and QA originals without stage/reset/clean. Hash and compare against remote refs and artifact provenance. Package only manifest-selected content into bounded encrypted chunks on Kingston; never produce a plaintext staging copy on a public/shared path. Preserve original source permissions and nofollow/symlink rules. Do not export Keychain secrets.
3. Before any S3 write, verify encrypted chunks can be decrypted with the independent recovery credential into an isolated scratch destination and that manifest/checksum counts agree. Refuse upload if the selected current generation exceeds **320 GiB**, the projected second retained generation would exceed **640 GiB** total, or the run would exceed **100,000** billable Tier-1 request units. These are proposed operator limits, not AWS-enforced account caps; a larger real minimum requires a revised approval, never silent omission.
4. Upload only encrypted chunks/manifest to the approved prefix over TLS; verify object length, S3 checksum/ETag semantics appropriate to multipart upload, returned version IDs and local SHA-256 of downloaded test chunks. Record encrypted manifest/root hash and run receipt in protected evidence. Do not turn on scheduled upload or broaden IAM.
5. Restore into an **independent isolated** destination, never the live Kingston source or Production. Verify hashes/decryption; representative dirty worktree and stash; compatible Postgres restore, Auth login, migration history, tenant/Site RLS denials, a private Storage object, Product startup and signed-package provenance. Measure RPO/RTO and actual AWS request/egress/storage usage. A source-file copy or successful S3 PUT alone is not backup readiness.
6. On failure, stop new uploads and revoke the short-lived writer session. Preserve existing source, bucket versions and error evidence; do not delete the only copy to save charges. Correct and repeat only under the approved byte/request budget. Bucket teardown or lifecycle deletion requires later explicit confirmation after independent restore and retention review. No disk First Aid or ownership change is part of this plan.
