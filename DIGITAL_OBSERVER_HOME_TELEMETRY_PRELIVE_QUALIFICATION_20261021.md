### Legacy authentication validation and later transactional procedure — NOT EXECUTED

The only deployed device authentication API for a legacy enrollment is the rotating `action=refresh` POST. It performs a compare-and-swap update to `video_gateway_device_enrollments.refresh_token_hash`, then returns a short-lived access token; it must **never** be used as a read-only credential probe. The hash function is SHA-256 of the refresh token. A genuinely non-mutating comparison is technically possible only if an approved read-only Production enrollment query can return the exact device record's `refresh_token_hash`, identity scheme, status and Site ID, and a trusted local process hashes the protected device token *in memory* and emits only a match/no-match result. No such authorized read-only Production hash retrieval was available or executed in this qualification. Keychain presence alone is not a match. Thus legacy credential validation remains **UNVERIFIED**, and the present operational path would require a separately approved state-changing transaction unless that read-only comparison is established.

Any later authorized transaction must be independently scoped to the Gateway `62df97e2-3c0b-427f-9108-bde029bc10e7` and Connector `db267b52-6282-4944-bcee-5d4857698fb0`, both bound to Site `cc1673b8-3eb0-4785-a12c-1fb88f425a41`; verify exact tenant and source assignments again before the window. Freeze one reporter at a time and pin the signed candidate artifact. Capture current QA health, source IDs, launchd/OTA definitions, secret-store accessibility, current monotonic proof sequences, backup digest, and the exact Production enrollment row/version through an approved read-only channel. Do not copy QA private keys or credentials to Production.

For each device separately, the client prepares a random next legacy token in its protected store **before** requesting refresh. The Production endpoint atomically changes the stored verifier from SHA-256(old) to SHA-256(next) only on an exact match; a successful response supplies a short-lived access token. The device atomically installs the next token locally and clears its prepared recovery record. On timeout or lost response, it retains the prepared record and retries old then prepared-next against the same enrollment, never generating an uncontrolled series of new tokens. Confirm the new verifier and access-token use with bounded telemetry and single-reporter checks. Abort on mismatch, repeated 401, Site/tenant discrepancy, unexpected second reporter, or source-health degradation. Never infer success from a request attempt alone.

Rollback means returning telemetry to the preserved QA identity and URL, verifying the original 10 DVR + 1 IP-source progression and all 17 canonical source IDs, and stopping any Production reporter before the QA reporter resumes. **It does not revert a Production token rotation.** Restoring an archived old token after Production accepted a new one would invalidate that legacy identity; use the prepared-next recovery path or an independently authorized re-enrollment. The Gateway Keychain item must remain accessible; no Keychain export or restore has been proven. The installed Connector must first be upgraded to a signed build containing the durable recovery change, or the transaction remains blocked. Exact restart/interruption time and real Production acceptance are unknown until a separately approved, instrumented live window. No such live write, restart, or authorization file occurred here.

The isolated recovery rehearsal did not stop or start either installed service. For a later separately approved rollback: first freeze and inspect the single active reporter per device; verify this archive's checksum; restore only the exact saved QA identity, launchd and OTA selection files to their original protected locations; validate permissions and plist syntax; start one service at a time; confirm its QA identity/auth and the 10 assigned DVR plus one IP-source progression before closing the window.
