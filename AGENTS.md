# Gan-Batuach project operating rules

This root file is the shared operating contract for Codex tasks working on this repository and its worktrees. Read the current canonical copy at the start of a task and again before a release; a running task must not assume that an older copy is current. A detached worktree or chat does not become synchronized merely because this file changed: reconcile its branch with the canonical version and explicitly hand off any outstanding work. User instructions and higher-priority system rules prevail.

## One source of truth and handoffs

- Git is the source of truth for code, migrations, infrastructure configuration, and documentation. Provider dashboards are the source of truth for live usage, invoices, settings, and deployment status. Never describe a local file or a successful push as proof that production is updated.
- Each task owns a branch or an explicit set of files. Before editing, inspect branch, working tree, relevant open PRs, and concurrent changes. Do not overwrite, stage, commit, stash, reset, or merge another task's work merely to obtain a clean tree.
- Keep a concise handoff for unfinished work: task/owner, branch and worktree, commit or PR, affected paths, migrations, validation, deployment status, blockers, and exact next action. The integration owner and the next explicitly authorized release owner must be able to find and reconcile it. A task is not "done" until its result is either verified in production or recorded as intentionally pending with a reason.
- Before ending a task, inspect the diff and status. Commit completed, scoped work to its branch when appropriate; avoid untracked, uncommitted, or unpushed completed work with no handoff. Never use a broad `git add .` in a shared dirty checkout. Do not claim that all chats are synchronized without checking their worktrees/branches and handoffs.

## Supabase: necessary data only

- For every new table, column, object, event, log, job, or integration, identify the business need, data owner, sensitivity, retention period, expected volume, query pattern, and cost. Reuse the existing model where sensible; do not create parallel copies, speculative tables, or test/demo data in production.
- Keep the database for transactional state and the minimum metadata needed by the product. Do not store raw video, continuous frames, large blobs, repeated snapshots, or verbose detector output in Postgres. Use an approved, private media path only when the product actually needs the artifact; store references and bounded metadata in Supabase. Keep live camera streams on the approved gateway/edge transport, not through Supabase Storage, database, or Vercel functions.
- Bound traffic at the source: select only required fields, scope by tenant and authorization, paginate and cap results, use appropriate indexes for measured queries, deduplicate and make writes idempotent, batch where safe, and use caching or backoff for repeat reads. Do not add high-frequency polling, per-frame writes, unbounded realtime subscriptions, repeated full-table scans, or noisy audit/telemetry writes. Preserve the security events actually required for incident response and compliance.
- Storage buckets must be private by default, with scoped access and short-lived signed URLs where needed. Define retention and cleanup for new artifacts before activation; review legal/security retention before deletion. Never purge production rows, evidence, audit history, backups, or user files merely to reduce a bill without explicit authorization and a verified recovery path.
- Before a change that can affect Supabase usage, capture relevant baseline and estimate impact on database size, storage, egress/bandwidth, requests, realtime, jobs, logs, and backups. After release, compare actual usage and error rates with the baseline. Investigate unusual egress by endpoint, bucket/object type, client polling, and media path before upgrading capacity. Respect existing quotas, spend caps, and alerts; escalate a projected limit breach with numbers and options.
- Before recommending a Supabase upgrade, compare measured headroom, required backup and restore capability, retention, expected growth, and the full monthly cost. Keep a tested recovery path for production changes; an upgrade is not a substitute for eliminating unnecessary traffic or storage.
- Every schema change is a new, ordered migration in `supabase/migrations/`. Do not edit an applied migration. Review RLS, tenant separation, grants, indexes, lock duration, backfill volume, rollback/recovery, and destructive SQL. Run `npm run qa:migrations` and relevant tests, then compare local migrations with the linked remote migration history. Apply only reviewed pending migrations in the release sequence; verify remote status and representative reads afterward. Never infer application from the presence of a SQL file alone.

## Non-negotiable unit economics: maximum ₪15 per user per month

- The project's all-in monthly cost ceiling is **₪15 per active paying user**. Use the count of distinct, real, active paying users as the conservative denominator; exclude staff, test/demo, duplicate, free, and inactive accounts. Also report total active users and cost per total active user for visibility, but never use a larger denominator to hide a breach. If there are no paying users, the ratio is undefined: report the full fixed monthly burn and the number of paying users needed to reach the ceiling; do not claim compliance.
- Include **every project-attributable expense** in the numerator: Supabase, Vercel, GitHub/CI, Codex/ChatGPT and other AI/development tools, domain/DNS, storage/CDN/media, gateway/compute, messaging/email/SMS/push, monitoring/security/backup, payment and integration fees, paid support, subscriptions, usage overages, and one-off charges in the month billed. Include taxes and currency-conversion effects in actual cash cost. For a shared account, use documented invoice-level allocation backed by usage; if reliable attribution is unavailable, conservatively include the whole bill and flag the uncertainty. Do not omit development costs merely because they are not yet production runtime costs.
- Maintain a single dated supplier cost ledger with plan, fixed fee, metered unit/rate, included quota, current usage, forecast usage, renewal, currency, exchange rate, taxes, hard cap/alert availability, project allocation, and invoice evidence. Reconcile actual invoices monthly; record estimates separately from verified amounts. Calculate `all-in monthly ₪ / active paying users`, fixed-cost break-even user count, marginal ₪ per additional user, and expected cost at current, 2×, and 5× demand, including realistic peak traffic, storage/egress, builds, backup retention, and AI usage. Never infer scalability from today's free tier alone.
- Before adding a vendor, changing a plan, enabling a billable feature, increasing a quota, or shipping a change that increases requests, storage, bandwidth, builds, AI tokens, messages, or backup volume, recalculate the **next-month and peak-demand** all-in forecast and its per-user figure. A proposal that could exceed ₪15, or whose cost cannot be bounded because metering/caps are unknown, is not eligible for activation or production release. Optimize usage or select a cheaper architecture first; surface the numbers and options to the user. Explicit approval is still required for any paid upgrade and does not silently waive this project ceiling.
- Set provider hard spend/usage caps where supported and alerts at approximately 70%, 85%, and 95% of the monthly project budget; where a hard cap is unavailable, use application-side rate limits, quotas, caching, bounded jobs, and a documented stop/degrade action before uncontrolled overage. Never solve a budget issue by disabling essential security logging, backups, retention obligations, or incident response. If current fixed commitments already exceed the ceiling at the current user count, immediately report the gap and break-even count, avoid new discretionary spend, and ask the owner to resolve the business constraint; do not pretend the ceiling is technically guaranteed.
- The owner-authorized release preflight checks current supplier spend and the updated all-in forecast against this ceiling before cost-incurring actions. The monthly supplier audit reconciles every invoice and user denominator; unexpected usage, a new supplier/plan, a pricing or exchange-rate change, or a material user-count/traffic shift triggers recalculation immediately rather than waiting for month-end. Keep the calculation and evidence in the restricted finance/supplier record, not in Git if it contains invoices or private account data; Git may hold only redacted totals and decision references.

## Verification model and evidence

- Classify every change before implementation: affected product journeys, data/tenants, vendors, infrastructure, security/privacy, cost, migration, and rollback. The change owner chooses the smallest meaningful test set from `DIGITAL_OBSERVER_CI_TEST_MANIFEST.md` and records what was run and what remains unverified. Passing a source-level test is not proof of a live provider, camera, restore, or production journey.
- Every PR must pass the six existing `Digital Observer CI` gates in `.github/workflows/production-checks.yml`: typecheck/lint, build, domain regression, security/isolation plus high/critical dependency audit and tracked-source secret checks, migration health, and release-contract preflight. Required checks must be green for the exact commit to merge. A skipped, timed-out, stale, or unavailable check is not a pass. Fix the cause and rerun; do not lower the gate.
- Add risk-specific verification before merge: integration tests in an isolated/test environment for changed provider or database contracts; authenticated role-boundary probes for auth, RLS, tenancy, media, or identity changes; controlled hardware E2E for gateway/camera/connector changes; and bounded production smoke after release. Never run destructive QA, demo seeders, or physical camera commands against production as a routine gate. Use the test tiers and hardware registry to distinguish simulated from real proof.
- Scan changed code and dependencies for secrets, vulnerable packages, unsafe permissions, unbounded queries, sensitive logging, and data-exposure paths. Review CodeQL and other actually enabled scanner results; a readiness placeholder or a limited regex scan does not count as a complete security audit. Track accepted findings with severity, owner, mitigation, due date, and recheck condition. Critical/high unmitigated findings block release unless a documented emergency risk decision is approved by the authorized owner.
- Keep redacted evidence for each release or audit: timestamp and environment, commit/PR, relevant commands or CI links, scanner versions/results, migration state, backup status, production smoke, Vercel/Supabase usage, owner, decision, and follow-up. Store pointers and non-sensitive summaries in the release ledger; never copy secrets, private media, invoices, or personal data into Git.

## Backup and recovery coverage across suppliers

- Maintain a current supplier/data inventory for **every active project provider**, including GitHub, Supabase, Vercel, domain/DNS provider, gateway/connector hosts, storage/media, identity, messaging/push, monitoring, payment, and AI providers as applicable. For each, state whether it holds unique production data or only reproducible configuration, the owner, backup/export mechanism, location, frequency, retention, encryption, access control, last successful backup, last tested restore, RPO/RTO, and recovery dependency. Mark `not applicable` only with a reason; do not assume a vendor's plan includes backups or that database backup covers storage objects, Auth, secrets, DNS, or local gateway state.
- Back up or export source code and critical configuration through approved, access-controlled mechanisms; keep a protected copy independent of the service being recovered where feasible. For Supabase, verify database and object-storage coverage separately. For Vercel and DNS, verify that environment-variable names, project settings, domains, routing, and DNS records can be reconstructed without exporting secret values into Git. For gateway/connector sites, verify local configuration, device identity, bounded queues, and evidence recovery according to their retention rules. For providers without a usable export, document a rebuild procedure and the residual loss risk.
- A row in `backup_readiness_checks`, `restore_test_runs`, or a supplier dashboard is a record, not proof. Verify a current vendor backup or export, integrity, and a restore into an isolated destination; check representative data, authorization, and measured RPO/RTO. Never overwrite production as a routine test. Preserve retention/legal holds and access logs. Failed, stale, missing, or untestable backups are tracked as open recovery gaps with an owner and deadline.
- Before a destructive migration, retention change, provider move, credential rotation affecting recoverability, or major release, confirm a recent recoverable backup of every affected asset and a tested rollback/rebuild path. If the recovery prerequisite is absent, stop that change and report the specific gap. Do not claim an untested backup is restorable.

## Check cadence and change triggers

- **Every PR/change:** run the six CI gates and the risk-specific tests above. Re-run checks after any material code, migration, configuration, or dependency change; green results from an older commit do not transfer. This is development validation, not an extra production deployment.
- **On explicit owner release authorization only:** reconcile the cumulative development and migration ledgers, freeze the candidate, and run the release gates below. No clock, restored credit, or completed task authorizes a release.
- **Monthly, on the first day of the month at 09:00 Asia/Jerusalem:** conduct a deeper read-only control review across all active suppliers: backup/export coverage and isolated restore evidence, disaster-recovery dependencies/RPO/RTO, access/MFA and secret age, domain/DNS/TLS, vulnerability and CodeQL results, dependency/licence inventory, RLS and role boundaries, audit/retention, incident backlog, cost/quotas, invoice routing, and security findings. Use the scheduled deep-security workflow once in that monthly cycle, plus its manual trigger when needed; avoid duplicate builds/scans. Produce a dated audit with pass/fail/not-applicable, evidence, owner, remediation, and next due date. A restore drill requiring an isolated environment must be coordinated and recorded; if it cannot be run, report `not tested`, not `pass`.
- **Immediately on a trigger:** auth/MFA/RLS/tenant/privacy/media changes require role-boundary and data-leak checks; schema/storage/retention changes require migration, backup and restore-path checks; dependency or secret changes require vulnerability/secret scans and rotation validation; gateway/camera/AI or notification changes require relevant integration and, when claimed, real-hardware/real-provider proof; payment/webhook changes require signature, idempotency and reconciliation checks; Vercel/DNS/provider configuration changes require target, TLS, failover and cost checks. A security incident, failed backup, unexpected spend/egress, outage, or high/critical scanner result starts incident triage immediately. Run the extra check before the affected change is merged or activated; do not wait for the monthly date.
