# PR #235 — Kingston ownership and signing readiness (non-live)

Date: 2026-10-21 (Asia/Jerusalem). Scope: read-only host audit, synthetic/isolated tests and a proposed change procedure. PR #235 remains Draft. No ownership setting, Production resource, installed camera service, Keychain item, credential or telemetry destination was changed.

## Decision

**Do not enable ownership on Kingston yet.** The external APFS volume is encrypted, writable and has about 1.72 TB free, but is mounted `noowners` (`GlobalPermissionsEnabled: false`). The existing private executor deliberately rejects this state. On the real host, its guard returned `false`; with only `noowners` removed from an **in-memory** copy of the actual mount options, the guard returned `true` when artifact-directory creation was deferred. This isolates `noowners` as the immediate filesystem-ownership blocker, not as the only remaining activation gate. The real artifact directory is absent. Neither test bypassed the real guard or ran a comparison.

The pinned APFS volume UUID is `D5D524FA-1545-43EE-AC1B-9771D2A7D526`. `diskutil info` reports APFS, `Encryption: true`, `FileVault: true`, `WritableVolume: true`, approximately 1.72 TB container free, and `SMARTStatus: Not Supported`. Mounted flags: `apfs, local, nodev, nosuid, journaled, noowners`. The currently displayed root/repository owner is the local user; under `noowners`, that displayed ownership is **not proof of the stored per-file UID/GID**. Current modes therefore cannot predict all post-change permissions.

## Isolated test limits

The existing 26/26 synthetic Kingston-guard suite includes `noowners` rejection, wrong UUID, missing mount, encryption failure and no fallback. An independent permission-mode check on an ownership-enforcing internal APFS data volume denied owner read at `000` and allowed it at `0600`; this validates basic POSIX behavior **only in that isolated environment**. A 128 MB synthetic APFS image was created in Kingston's restricted test area, but `hdiutil attach` returned permission denied, even under the approved elevated tool path. The unmounted, synthetic image and empty mountpoint were removed. **No Kingston ownership-toggle rehearsal occurred.** The test is insufficient to claim compatibility for the 112 worktrees, containers, Xcode or Edge packages. An owner-approved isolated APFS volume/mount-capable session, or an equivalent representative clone with independently verified ownership metadata, remains required.

## Proposed non-destructive change and rollback — NOT EXECUTED

1. Owner separately approves a maintenance window and volume-wide ownership change. First prove independent recoverable backups of Kingston's Git/unique local work, isolated Development database and Colima state, Xcode sources/configuration, and protected Edge configuration. Recheck the 36-file archive and Keychain presence. Arrange offline Disk Utility First Aid for the previous warnings; stop if repair reports unresolved damage. Capture worktree status, volume UUID, current mount flags, key path modes/ACLs and running-process inventory. Do not move the environment to the internal SSD.
2. Close Xcode and quiesce only the affected Development Docker/Colima and Git writers using their supported shutdown procedures. Do not restart or alter the installed Home Gateway/Connector. Rehearse on a mountable isolated APFS test volume first. Test representative Git write/lock, Development database access, container mounts, Xcode build storage and signed-package verification. Abort on unexpected ownership.
3. The supported GUI procedure is Finder → select `DIGITAL_OBSERVER` → Get Info → Sharing & Permissions → clear “Ignore ownership on this volume” (administrator required). The macOS `diskutil(8)` equivalent is `sudo diskutil enableOwnership /Volumes/DIGITAL_OBSERVER`. **These are review-only instructions, not commands run in this task.** Target the exact mounted volume/UUID, never a parent device or another volume.
4. Verify `GlobalPermissionsEnabled: true` with `diskutil info`, absence of `noowners` in `mount`, the unchanged volume UUID and encryption, plus bounded access checks for each affected workload. Do not recursively `chown` or weaken modes. The private executor also requires an owner-only artifact directory and all separate signing/approval/Production-access gates; enabling ownership alone never authorizes comparison.
5. On breakage, quiesce writers and use Finder's original checkbox or `sudo diskutil disableOwnership /Volumes/DIGITAL_OBSERVER`, then verify `noowners` and original Development behavior. This setting is persistent for the current macOS host. **Disabling ownership does not undo metadata written while enforcement was active.** Restore affected data only from an independently verified backup and separately approved recovery procedure. A toggle-back is not proof of complete rollback.

Apple's [Mac permissions guidance](https://support.apple.com/en-bh/guide/mac-help/mchlp1204/mac) documents the Finder checkbox; local `man diskutil` documents `enableOwnership`/`disableOwnership`, root requirement and host-persistent volume-database behavior. Apple's [Disk Utility First Aid guidance](https://support.apple.com/en-gb/guide/disk-utility/-dskutl1040/mac) describes repair order and limits. No volume-wide command was executed.

## Signing and independently verifiable audit

`security find-identity -v -p codesigning` returned **0 valid identities**. Xcode 26.3 and the existing Personal Team iPhone QA signing do not provide a verified signing identity/trust policy for this one-shot macOS executor. Existing Connector QA artifacts are ad-hoc signed and can pass local seal verification, but an ad-hoc signature is not an independent project authorization. The Edge OTA pipeline has a separately pinned Ed25519 trust registry and historical AWS KMS-backed manifest-signing path; this task has no active AWS CLI/signing session or signed candidate manifest. Local macOS execution signing and OTA archive/manifest signing are distinct gates. No identity or key was created or exported. See Apple [TN2206](https://developer.apple.com/library/archive/technotes/tn2206/) and the repo's `edge-release-trust.mjs`/`edge-update-contract.mjs`.

The existing SQLite approval store uses `BEGIN IMMEDIATE`, two attempts, short-lived approval and append-only triggers, but its file owner can replace the database: this is **not immutable audit**. Proposed independent receipt: canonicalize a redacted event containing request ID, exact pinned device binding, actor ID, approval ID, purpose, timestamp, phase, outcome and prior receipt hash; hash and sign the chain head with a separately protected, approved signing key; publish the signed checkpoint to an independently controlled append-only/WORM destination; verify sequence, signature, continuity and revocation from an independent reader before permitting execution. Never include credentials, verifiers, bearer tokens or raw media. Fail closed if checkpoint acknowledgement or verification fails. Existing AWS trust infrastructure may be a candidate signing root **only after custody, permission, cost and independent storage review**; the current task does not activate it. No external anchor or independently verifiable Production audit sink exists yet, so immutable audit remains **BLOCKED**.
