# Management privacy self-profile delivery — bounded development slice

Source Development SHA: `416003a26593c6a4b3406c85e5aa285fbdef42b7`. Candidate branch: `codex/gb-privacy-access-export-fulfillment-20261114`. This is a Development-only implementation; no Production or real subject data was exported.

## Exact coverage

An Admin may issue a short-lived delivery grant only for an approved Management `access` or `export` request whose requester and subject are the same active profile, with explicit `profiles` scope count one, no scope retention/hold block, no active legal hold, and no Child, Garden or Digital Observer context. The requester can then make at most three authenticated reads within 24 hours. The response is generated from the current canonical `profiles` row and contains only full name, phone, role and profile creation time; oversized name/phone fields are refused rather than truncated. Access renders JSON in the browser; export downloads that same limited JSON as an attachment. Both surfaces explicitly say “self profile only.”

The grant stores request and actor identifiers, issuance/expiry/revocation timestamps, access count and last access time. It stores no duplicate profile data or export blob. The route uses the caller's session, not a service key; there is no public bucket, signed object URL or external provider. The response has `private, no-store, max-age=0`, a sandboxed content security policy, `no-referrer` and `nosniff`. Each new grant, revocation and successful read writes an immutable audit event in the same database transaction. A failed audit insert rolls the grant or read back. Repeated issue/revoke calls are idempotent; expired and revoked grants cannot be reissued for the same request. Existing Management completion rules remain authoritative, so a partial self-profile delivery does **not** mark the privacy request completed.

This is deliberately **not** a full access/export right fulfillment. Child, Garden, documents, payments, messages, health, other profile fields and Digital Observer data are excluded. Correction, deletion, notification and broader verified delivery remain open. A legal/retention decision for this metadata and a complete supplier cost assessment remain release gates.

## Data and cost classification

Business need: deliver a verified, limited self-profile subset without another personal-data copy. Data owner: Gan Batuach Management privacy administrator. Sensitivity: personal data; grant metadata and immutable audit events are restricted. Query pattern: one Admin issue/revoke and at most three requester reads per approved self request. Bound: one grant row per request, ≤3 audited read events, 24-hour live window and ≤640 bytes of name/phone UTF-8 fields before JSON overhead. The grant row remains as a no-reissue and audit-link tombstone after expiry; its final retention period is **not legally approved** and needs review against privacy-request and audit retention, not silent deletion. No scheduled cleanup is claimed.

No new paid dependency or fixed monthly commitment is introduced (`₪0` incremental fixed fee). Actual all-in supplier spend, taxes and active paying-user count were not verified in this source unit. The confirmed paying-user denominator is zero, so ₪15 per paying user is undefined; the project’s ₪1,000 prelaunch operating cap cannot be certified from these tests. Before any Production activation, reconcile the restricted supplier ledger, forecast actual query/audit volume and verify the cap with the owner.
