## Service dependency and return path

- The seven pinned containers have `restart=unless-stopped`. Docker [documents](https://docs.docker.com/engine/containers/start-containers-automatically/) that manually stopped containers with this policy **do not automatically restart even after daemon restart**. Their exact IDs must be started and verified deliberately. The daemon currently reports `LiveRestoreEnabled=false`. A persistent daemon/socket failure would prevent Docker API exact-ID start; a VM failure would also remove the guest shell path. The preceding synthetic daemon-fault receipt `cf432290` did not qualify exact-ID recovery through such a failure.
- Docker [documents](https://docs.docker.com/reference/cli/docker/container/stop/) a graceful signal followed by a forced kill after the stop timeout. The installed `colima stop [profile]` / `colima start [profile]` commands exist, but stopping the whole VM would make the guest-mounted volume directories inaccessible until restart or an independently qualified offline ext4 attach. The Mac has no `guestfish` or `qemu-nbd` tool installed; no offline read-only attach or current-state restore has been demonstrated. The only *identified* route plausibly within 1 GiB is stopping the seven **Development containers while leaving the original VM/daemon running**, then reading the two quiescent volume trees through the guest. This route was **not** exercised.
- Kong alone publishes Development API at `127.0.0.1:55421`; the prior DB receipt records `127.0.0.1:55422`. A host `lsof` snapshot found two `ssh` listeners and **zero established clients** on these ports. The inspected LaunchAgent/LaunchDaemon plist text had no direct `55421`/`55422`/`colima-gbi` reference. These are bounded observations, not proof that an on-demand Development client, Home service or local Production process will never connect. The separate default-home `push38t` profile and the original `gbi` have different profile homes; no shared Docker volume was found on the original daemon. Neither Home nor Production was accessed or changed.
- Planned downtime would make local Supabase Auth, Storage, REST, Realtime and Kong unavailable, so both Development products and any local QA depending on 55421/55422 could fail. A successful cold archive would still require `age` integrity verification, exact DB/Storage metadata reconciliation, an **isolated encrypted restore** and successful restart/health/auth checks on the *same* source before claiming recovery. No such current-state cold stop/restart rehearsal or rollback exists. If the daemon or VM fails before the archive is complete, only the original on-Kingston volumes and older recovery material remain; there is no independently verified **current** copy.

## Decision and single next technical path

**NO-GO; do not request source downtime yet.** Volume-only bytes appear small enough for a guarded 1 GiB archive, but this does not outweigh the unqualified exact-ID return and offline VM-failure recovery path. An uncompressed full two-disk safety copy exceeds the 1 GiB cap at measured allocation; no compressed result below the cap was measured. The older encrypted backup cannot be represented as a current rollback. Stopping the original source without first proving return/independent custody would make an irreversible loss or prolonged outage risk unbounded by this inspection. No claim is made that a PostgreSQL crash would occur or that the database is corrupt.

**One focused alternative:** rehearse the *same seven-service stop → guest-side two-volume encrypted export → exact-ID start → isolated encrypted restore* sequence on a disposable, disjoint synthetic Colima/Docker fixture using cached images and no original volumes, including a daemon-unavailable fault and a hard 1 GiB/3 GiB guard. Only if that passes should a separate original-source preflight verify independent current-state rollback and real dependencies, then formulate an owner downtime approval with a maximum window, exact seven containers, abort thresholds and rollback. A synthetic PASS would not itself prove original `gbi` recovery or authorize shutdown.
