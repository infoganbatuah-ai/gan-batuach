# Five synthetic age components: full isolated restore rehearsal

**2026-10-28, review-only. Result: synthetic five-component restore PASS; real Development restore NOT RUN.** The source was a freshly created PostgreSQL 17.6 fixture and one fake Storage object inside a disposable encrypted Lima guest. No real component receipt/ciphertext, owner age key, Notes, clipboard, Development SQL, Production or Home data entered this run.

## Actual isolated sequence and checks

1. Reused the 12-GiB AES-256 scratch sparsebundle and the same no-host-mount Lima guest. Its network-deny rules, negative IPv4/IPv6/DNS probes, reboot persistence, no proxy, no original volumes and `--network none` data containers were measured in-process before the five-component receipt gate.
2. Generated three separate synthetic PostgreSQL custom archives (`_supabase`, `gan_batuach_baseline_builder_v2`, `postgres`), globals and a Storage tar. Encrypted each to a disposable age recipient and verified all five ciphertext sizes/SHA-256, exact IDs, synthetic scope, recipient, source-container identity and 1-GiB cumulative cap. No real receipt was accepted.
3. Passed the synthetic identity through PTY to an inherited FD for `age -d`. All five authenticated plaintext components remained on the encrypted scratch mount or inside that guest's encrypted disk. Verified the Storage tar against its file manifest before extraction. Wrong key, tamper of each ciphertext, receipt mismatch, deadline and an authenticated but content-corrupt Storage tar were denied; no failed decrypt left a plaintext output.
4. Copied those authenticated synthetic components into the same guest and restored globals into each of three **new, separate PostgreSQL volumes/clusters**. Restored each custom archive into its corresponding new database with `pg_restore --single-transaction --exit-on-error`. In all three, queried the recovered sentinel and known synthetic migration `synthetic_0001`. Verified the restored `postgres` cluster contains the synthetic Auth user, the `qa_restored_reader` role, its SELECT grant, the enabled RLS policy and an actual `SET ROLE qa_restored_reader` query that reveals only the allowed Tenant row. No existing source volume was reused as a target.
5. Extracted the already manifest-verified Storage tar into a new volume, then compared the recovered file bytes with the restored `storage.objects` name, size and SHA-256 record.
6. Injected a failure **after globals had committed** in a fourth fresh PostgreSQL target: a truncated custom dump was rejected by `pg_restore`, the target was not reported as restored, and its partial volume was removed and verified absent. All staged guest plaintext files were removed. The guest stopped, the encrypted image detached and its exact scratch directory was deleted; final `scratchCleaned=true` and no `.restore-architecture-qa.*` directory remained.

The final run exited 0 with `ARCHITECTURE_PROBE_PASS` and true values for `syntheticAgeGlobalsRestored`, `syntheticAgeThreeDatabasesRestored`, `syntheticAgeAuthRolesRlsMigrationsVerified`, `syntheticAgeStorageMetadataBytesMatched`, `syntheticRestoreFaultCleaned`, `syntheticGuestStageCleaned`, all five-component preflight flags, all network-denial flags and `scratchCleaned`. JavaScript syntax, the 24 focused component-preflight tests and Git diff integrity checks were run separately.

An intermediate run failed **after** the new restore had passed because an older direct-pipe test (without globals) tried to restore an RLS policy referencing an absent role. That redundant weaker test was removed; the five-age path is now the only restore path. A subsequent run passed restore but initially hit a transient normal image-detach failure. The stopped guest and absence of open files were checked, the exact image was normally detached and its synthetic scratch was removed manually. A bounded normal-detach retry was added; the final run cleaned itself. No forced detach or unrelated deletion occurred.

## Qualification boundary

This verifies mechanics for deliberately small **synthetic** fixtures, not the actual Supabase schema, real Auth records, all 257 migrations, Production compatibility, real Storage object inventory, cross-store atomicity, or a current-state rollback point. The original five-component capture remains `COMPONENT_BACKUPS_ONLY` and `independentRestore=NOT_RUN`. The direct real restore CLI remains disabled. [PostgreSQL's restore documentation](https://www.postgresql.org/docs/17/app-pgrestore.html) notes that restoring a dump executes SQL chosen by the source superuser; any future real restore must remain in a separately verified, disposable, no-egress destination.

Do not claim real restore PASS until that execution and cleanup actually succeed.
