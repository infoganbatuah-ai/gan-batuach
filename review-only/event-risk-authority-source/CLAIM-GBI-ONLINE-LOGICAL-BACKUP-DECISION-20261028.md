# Original `gbi` online logical backup — bounded decision

**2026-10-28. Decision: limited GO for independently labelled component backups; NO-GO for a current, atomic Development-plus-Storage recovery point.** This is an offline review of existing capture code and receipts, not a new backup, restore, source operation, or key check.

## Evidence reused

- The three prior encrypted capture attempts are recorded in `CLAIM-CURRENT-DEVELOPMENT-ENCRYPTED-CAPTURE-20261027.md`: twice `SOURCE_WAL_MOVED_BEFORE_CAPTURE`, then `SOURCE_WAL_CHANGED_DURING_CAPTURE`; the only partial ciphertext was removed. No current snapshot or restore PASS exists.
- The original external-home `gbi` source was separately pinned in `CLAIM-GBI-COLD-STOP-NOGO-20261028.md`: the exact daemon, seven project containers, two named volumes, disjoint QA container and configuration matched at that read-only instant. The cold-stop path remains NO-GO.
- `capture-current-development-encrypted.mjs` runs three sequential `pg_dump -Fc` commands, `pg_dumpall --globals-only`, and a separate Storage tar. It requires unchanged cluster WAL from before the first dump through after the Storage tar. That is an intentionally stronger *cross-component* gate, not a requirement for an individual `pg_dump` snapshot. Removing it without changing the success claim would be unsafe.
- PostgreSQL documents that `pg_dump` can produce a consistent export of one database while it is being used, and `pg_dumpall` handles cluster-global objects separately ([PostgreSQL 17 `pg_dump`](https://www.postgresql.org/docs/17/app-pgdump.html), [`pg_dumpall`](https://www.postgresql.org/docs/17/app-pg-dumpall.html)). The three sequential database dumps, globals export and file Storage capture have **no common snapshot** under concurrent writes. Supabase database backups omit actual Storage object bytes ([Supabase backup guidance](https://supabase.com/docs/guides/platform/backups)).
- The installed Storage file backend can write bytes before metadata commit and delete bytes separately from the database transaction; the exact local version/write paths are recorded in `CLAIM-CURRENT-DEVELOPMENT-STORAGE-ONLY-BARRIER-20261027.md`. Pre/post tar hashes or two equal samples cannot exclude an intervening change/reversion or prove metadata-byte atomicity.

## Executable boundary for a later authorized capture

1. A no-downtime **component** capture can use the original running `gbi` with read-only `pg_dump -Fc` of each pinned database, globals separately, and separately encrypted Storage object bytes. Label each database's consistency individually, record its capture interval, server/tool version, source identity, actual ciphertext bytes and SHA-256. Do not label the set an atomic cluster/Storage snapshot or a verified current-state rollback.
2. Replace the existing script's `walUnchanged`/`stableSourceWindow` PASS claim before use; retain exact source pins, no Production fallback, encryption-only streams, 1 GiB cumulative ciphertext cap, 3 GiB internal-free floor, timeout, private output permissions and removal of **only newly incomplete** output. An isolated restore must separately validate Auth/schema/roles/migrations, each database, actual Storage bytes and metadata; a component restore is not full Product recovery proof.
3. For Storage, record an object-level metadata identity/version/size inventory and object-byte hashes, plus exceptions and time bounds. A moving or missing object is a failed component capture requiring safe retry; even a matching result is not proof of cross-store atomicity while privileged writers remain un-fenced.
4. A whole-running-cluster `pg_basebackup` is a different method: it initiates a checkpoint/backup mode and handles WAL, so it is not a source-read-only operation under the present boundary. It also cannot make the separate Storage filesystem atomic. Do not substitute a raw VM disk copy.

## Gate result and next action

**Limited GO is a method qualification, not permission to run the old script unchanged.** The independent owner-held `age` identity was compatible with an older artifact in a prior receipt, but no fresh key test was performed here. The owner's latest statement says a key was copied to the Mac clipboard; this unit did not read or persist it. Before actual capture, a separate secret-safe execution must verify that identity in memory against the pinned public recipient, clear the clipboard, recheck live source/capacity, and use a revised component-labelled capture with an isolated restore. No source stop/start/pause, SQL, key read, object-byte read, capture, restore, provider access or Git remote operation occurred in this decision unit.

**Full Development recovery point: NO-GO** until a positively enforced common writer barrier or a proven version-retention/transactional cross-store mechanism exists. Neither the previous WAL equality failure nor a future component backup should be relabelled as a full current-state rollback. The next engineering step is a scoped, offline change to the capture/receipt contract that makes the component-only guarantee explicit and testable; after independent key proof, execute one bounded real capture and isolated restore only under the existing owner authorization and limits.

## Offline implementation addendum (same date)

- `capture-current-development-encrypted.mjs` now requires the explicit `--capture-components-only` mode and can emit only `COMPONENT_BACKUPS_ONLY` or `BLOCKED`. Its receipt hard-codes `atomicSnapshot=false`, `verifiedCurrentRollback=false`, `restoreVerified=false`. No code path retains the former cluster-WAL-equality or `stableSourceWindow` PASS claim. Each database and globals item has its own capture interval, source/version identity, ciphertext byte count and SHA-256. A completed earlier component remains recorded if a later one fails; a partial new ciphertext is removed.
- The existing bounded ciphertext writer is now used with the **remaining cumulative** allowance: at most 1,073,741,824 encrypted bytes across components, a 3,221,225,472-byte free-space floor, private `wx` output and upstream abort. An exclusive `wx` run lock prevents concurrent local captures; a stale lock fails closed pending inspection. Removal of an invalidated completed component checks its task-created inode; an existing or replaced archive is not deleted. The capture has a 180-second overall deadline, including bounded synchronous probes. These are code-level limits, not a real source run.
- Storage has a separate source-side file inventory of opaque path hashes, file sizes and SHA-256 hashes, with a file/count cap and refusal of symlinks or file changes during hashing. Read-only `storage.objects` row digest and count are sampled before and after its encrypted tar. Any detected disappearance, addition, content change or metadata change invalidates **only** the newly captured Storage ciphertext and blocks the set. The sampled file hashes are not asserted to be hashes parsed from the encrypted tar; `metadataObjectMapping` and per-object archive verification remain `NOT_PROVEN`. An intervening change-and-reversion cannot be excluded. A physical restore, Auth/schema and object/metadata reconciliation remain required for recovery qualification.
- Offline validation: `node --check` on changed modules, **26/26** focused Node tests (including the existing bounded-writer suite), and `git diff --check` passed. The CLI's no-flag fail-closed path was exercised without Docker/SQL. No key/clipboard access, real `gbi` capture, restore, source read, service operation, supplier operation or remote Git action was performed. Before a real run, the owner-held recovery identity still needs a fresh secret-safe match to the pinned public recipient; the running Storage image's Node inventory command and the metadata COPY must be qualified against the exact isolated source. The resulting component set cannot be called an atomic current-state rollback even if every file succeeds.
