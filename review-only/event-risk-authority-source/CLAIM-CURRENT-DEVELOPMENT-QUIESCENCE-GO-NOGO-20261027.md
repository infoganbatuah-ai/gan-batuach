## GO/NO-GO decision

**NO-GO.** A filesystem lock, PID scan, Docker socket mode check, or temporary API/direct-DB firewall rule is cooperative or momentary; it cannot enforce exclusion of *all* future privileged `docker exec`, `docker run --mount`, guest-root or Lima-SSH writers while a live Docker daemon is required to keep PostgreSQL available. The original source has no scoped Docker authorization plugin. The necessary independent automatic exact-ID resume is also unproven when the daemon remains down; `LiveRestoreEnabled=false` makes a daemon shutdown unsuitable as a harmless access lock. Thus there is no sufficiently bounded, enforceable source quiescence + rollback contract to present for owner approval now. This is a control-plane limitation, **not** database corruption.

Changing the source to install an authorization plugin, altering socket/group permissions, stopping Docker, restarting/repairing `gbi`, or using guest-root/containerd intervention would cross the present no-mutation boundary and could interrupt the Development database. None was attempted. Because these interventions still cannot constrain a root administrator and exact resume under persistent daemon failure, a narrow rehearsal approval would not by itself close the strict gate. No owner action is requested at this point.

## Focused transition

Switch the next feasibility unit to **online PostgreSQL whole-cluster backup plus a separately established Storage-object/metadata consistency barrier**, rather than another quiescence/TCP experiment. An online PostgreSQL base backup is a supported database primitive but it is not a complete Supabase Storage backup, and its source checkpoint/WAL behavior requires its own authorization before execution; neither is performed here. The **single next read-only check** is to trace the canonical Development Storage write path and metadata commit path against the existing volume/API configuration to determine whether one bounded, reversible **Storage-only** object/metadata barrier can be established without pausing PostgreSQL or touching Home/Production. If that relationship cannot be proven, mark the online combined backup BLOCKED rather than treating separate timestamps or WAL equality as consistency proof.
