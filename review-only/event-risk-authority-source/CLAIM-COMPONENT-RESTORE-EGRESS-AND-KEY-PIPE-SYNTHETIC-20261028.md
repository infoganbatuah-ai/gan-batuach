## Real-data gate: NO-GO at this stage

A complete real-data restore controller has not yet joined these pieces. Before invoking the owner-held key again, it must pin the five ciphertexts and restricted receipt; verify exact hashes/sizes and free-space/time limits; verify a freshly created encrypted, disjoint target with guest-wide egress denial **before** copying any plaintext into it; pass the owner key directly from hidden local TTY to `age` by pipe (not argv, environment, source, chat, clipboard, log or permanent plaintext key file); stage authenticated plaintext **only inside that encrypted target**; run the Storage tar gate before extraction; restore globals and all three PostgreSQL 17.6 custom archives into distinct new databases with error-stop; verify Auth, schema, migration history, roles/grants/RLS and representative data; reconcile Storage metadata with actual object bytes; then stop, detach, verify cleanup and preserve a sanitized receipt. Corrupt or partial decrypt must never be labelled restored. The source VM and volumes must never be mounted into the target or changed by that process.

PostgreSQL warns that restoring a dump executes source-superuser-selected code. The original Development source is trusted for this purpose only in a separately verified, network-isolated, disposable destination; a successful `pg_restore --list` or a synthetic sentinel is not a complete restore proof. The component captures were sequential, so even a successful isolated restore cannot establish cross-database/Storage atomicity or a current-state rollback point.
