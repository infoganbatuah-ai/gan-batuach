## Candidate A — online whole-cluster base backup plus Storage barrier

PostgreSQL 17 `pg_basebackup` captures the **whole running cluster** (all three databases and globals) with required WAL and is inherently compatible with concurrent database writes. It initiates a source checkpoint and backup mode and, with WAL streaming, ordinarily uses a temporary replication slot. Thus it is **not a read-only source operation**, even without SQL DML. The one-stdout tar option requires no extra tablespaces and **no WAL streaming**; `-X fetch` would require retaining WAL until completion, which `wal_keep_size=0` does not guarantee under continued writes. The default `-X stream` produces separate base and WAL tar files, so an encrypted-only bounded multi-stream transport would need to be qualified. None has been run. See [PostgreSQL 17 `pg_basebackup`](https://www.postgresql.org/docs/17/app-pgbasebackup.html).

Even a valid cluster backup covers only database Storage **metadata**, not the actual separate Storage object bytes. A coordinated, enforceable Storage-write and Storage-metadata barrier is needed across the base-backup recovery point. A pre/post filesystem digest alone cannot prove that no object changed and changed back or that metadata and bytes share one point in time. Supabase confirms database backups do not include Storage objects: [Supabase database backups](https://supabase.com/docs/guides/platform/backups). Source checkpoint/backup mode, potential WAL retention, and the missing cross-store barrier put this candidate **outside the current no-source-change delegation**.

Safety/rollback if separately authorized later: verify the original source and replication prerequisites; establish the Storage/metadata barrier first; use a bounded encrypted-only stream with 1 GiB/3 GiB fail-closed guards; abort and remove only newly created incomplete ciphertext on any error; release the barrier and ensure no retained slot/WAL pressure; preserve original files. A physical restore would require a separately qualified PostgreSQL 17 isolated guest and its own integrity/`pg_verifybackup` and application/Auth/Storage checks. The existing logical-restore synthetic result does **not** qualify physical restore.

## Candidate B — bounded Development writer quiescence, then logical dumps

With a proven common write-free window, the existing `pg_dump -Fc` per-database plus `pg_dumpall --globals-only` and a separate Storage byte archive can form a coherent set. `pg_dump` itself gives a consistent **single-database** snapshot under concurrent activity, but it does not synchronize multiple databases or filesystem Storage; PostgreSQL documents the distinction in [PostgreSQL 17 `pg_dump`](https://www.postgresql.org/docs/17/app-pgdump.html) and [PostgreSQL 17 `pg_dumpall`](https://www.postgresql.org/docs/17/app-pg-dumpall.html).

The six visible Development service containers (Kong, Auth, REST, Realtime, Storage, inbucket) are not a complete proven writer inventory: direct loopback clients and in-database `pg_cron`/`pg_net` work can remain. Pausing/stopping services changes Development runtime, and disabling scheduled jobs would require a separate reviewed source operation. No such action is authorized by this read-only unit. The current script's strict WAL equality is fail-closed, but WAL movement alone is **not** a supported proof that logical rows changed; conversely, replacing it with sampled tuple counters would be too weak for a cross-store guarantee. A full writer inventory and a positive, reversible write barrier are prerequisites.

Safety/rollback if separately authorized later: pin and inventory every Development writer and its resume procedure; verify no Production/Home or unrelated Colima container shares the target; install an automatic bounded resume watchdog; prove the barrier before capture and maintain it through all three dumps, globals and Storage; enforce the existing encrypted-byte and disk-free limits; on any failure discard only the new ciphertext and resume exactly the paused Development writers. Recheck service health and application Auth afterward. The existing isolated encrypted scratch guest can then be requalified for a real **logical** restore and object-byte/metadata reconciliation, without using the original database as a target. No restore is claimed here.
