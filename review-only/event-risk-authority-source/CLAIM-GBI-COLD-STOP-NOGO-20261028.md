# Original `gbi` cold-stop decision — NO-GO

**2026-10-28, read-only source preflight and offline code review.** No source service, VM, database, volume or key was changed. `gbi-readonly-preflight.mjs --read-only` returned `PINS_MATCH_NOT_GO`: daemon `cb406f3c-6987-4019-8ac7-bed803bf6a37`, seven exact running project containers, the two expected local volume mounts and the disjoint running QA container matched; Colima config digest matched. Internal free was **16,613,482,496 bytes** at that instant. This is a point sample, not writer exclusivity or future capacity proof.

The exact running containers advertise `SIGQUIT` for Kong, `SIGINT` for PostgreSQL and default `SIGTERM` for the other five. Docker reports shell-form `Path=sh` in the Kong and PostgreSQL container configuration; current process-name inspection showed nginx and a PostgreSQL wrapper, but read-only inspection cannot prove every signal-handling and clean-shutdown outcome. The configured signals must not be replaced by a generic signal without qualification.

Docker's [stop command](https://docs.docker.com/reference/cli/docker/container/stop/) escalates to `SIGKILL` after any finite timeout. Its `-1` timeout avoids forced kill but waits indefinitely. Docker's [signal-only kill command](https://docs.docker.com/reference/cli/docker/container/kill/) can send a chosen non-`SIGKILL` signal, but that signal may not terminate the container; cancelling the client timer cannot retract a signal already sent. A container may therefore exit **after** a controller's timeout or after a momentary “running” check. The planned 15-minute source-return window cannot be enforced by these mechanisms without either risking `SIGKILL` or retaining a late-stop/outage risk. No source-specific no-SIGKILL stop/restart adapter was built or invoked.

The previous controller also accepted a caller-supplied approval object and did not verify every adapter method before the first stop. It now refuses all non-fixture adapters, checks every required method first, verifies each container is stopped before the next, waits for PostgreSQL health before dependent restarts, and never reports source-return PASS after an unconfirmed/late stop. The approval object is **simulation input only**; it is not owner authorization. Focused fake tests passed. This closes false-success paths, not the source runtime gate.

**Decision: NO-GO for the proposed cold backup now.** The owner cannot make a technically unbounded stop/restart path safe merely by accepting risk. Additionally there is no independent backup of the **current** state before stopping, writer exclusivity is not established for a future window, and the owner-held private identity was not checked in this unit. An older backup may not contain the latest Development writes. A daemon/VM outage or late stop could leave them unavailable or lost. No cold-stop approval request should be presented as if these facts were resolved.

**One bounded alternative to select:** keep the original `gbi` running and prepare a no-downtime, encrypted logical PostgreSQL backup plus a separate Storage-object byte capture. Use the original isolated Development identity, `pg_dump`/globals with consistency verification, per-object hashes and metadata reconciliation, abort/retry on concurrent object changes, and a disjoint restore proof. Do not claim an atomic database-plus-object snapshot unless a supported writer fence is actually demonstrated. No S3 upload, Production/Home change or paid resource is included. If this alternative is not accepted or its consistency gate fails, preserve the running source and report the exact gap; do not fall back silently to cold stop.

**Remaining runtime facts before any future cold proposal:** independent owner key proof, exact source re-pin, legitimate writer exclusion for the full window, source-specific graceful signal handling and clean PostgreSQL shutdown, late-stop-safe restart under daemon failure, real per-file manifest and post-export equality, output inode/partial-file ownership, and an independent current-state recovery path. Offline tests or the read-only pin sample do not satisfy them.
