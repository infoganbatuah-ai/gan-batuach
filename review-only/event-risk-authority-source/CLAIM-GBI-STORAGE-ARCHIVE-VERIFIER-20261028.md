# Storage component archive verification gate — offline implementation

**2026-10-28, review-only.** This unit adds a streaming verifier for the existing component-only Storage tar, not a capture, decrypt, restore, or current-state rollback result. Cold backup remains **NO-GO**; online backup remains **COMPONENT_BACKUPS_ONLY** if separately executed and qualified. No real Storage data or owner key was read here.

## Exact local contract

- `capture-current-development-encrypted.mjs` invokes the original Storage container's `/bin/tar -C /mnt -cf - .` and streams that stdout directly into `age`. The source-side `storage-file-inventory-noatime.py` independently computes SHA-256 of each relative UTF-8 file path, logical byte count and file SHA-256 using `O_NOATIME|O_NOFOLLOW`, before and after capture. The component receipt records those opaque triples in `details.sampledSourceFileManifest` and currently marks archive-per-object verification and metadata mapping `NOT_PROVEN`.
- Read-only `tar --help` identified BusyBox **1.37.0**. A non-Storage system-entry header probe produced magic bytes `75 73 74 61 72 20 20 00` (`ustar`); no Storage object was opened by this probe. The parser accepts USTAR headers, including the observed GNU-compatible magic prefix, and refuses unsupported PAX/GNU extension entries rather than guessing how to interpret them. A future real archive with an unsupported extension is a specific **NO-GO** for this gate until the parser is safely extended and retested.
- `verify-decrypted-storage-tar.mjs` consumes only a tar byte stream. It never extracts or writes plaintext. It computes the same relative-path digest, file size and SHA-256 as the `O_NOATIME` inventory, compares them as a set (order-independent), and rejects missing, extra, changed or duplicate files. Directories are allowed but may not collide with files; root may appear once. It rejects absolute and traversing paths, malformed UTF-8, symlinks, hardlinks, devices, FIFO, extension records, nonzero link fields, bad USTAR checksums/size fields, nonzero padding, truncated bodies and absent two-block terminators. It caps files at 20,000, logical bytes at 1 GiB, archive bytes at 1 GiB plus bounded overhead, and total entries at 160,001. Abort is fail-closed.
- `storage-restore-archive-gate.mjs --receipt <protected-receipt>` is the future isolated restore entry point: supply the separately decrypted Storage tar on stdin only after independent key verification and a separately approved restore. It reads a capped receipt and emits only status, count, total logical bytes and an opaque manifest digest. Errors are generic codes. It does **not** decrypt, stage plaintext, extract, compare metadata rows or activate restore. Run this gate before any separately designed isolated extraction; a later extraction still needs its own destination/path safety and post-extraction verification.

## Evidence and limits

- Focused synthetic USTAR tests cover matching and reordered files, content/size mismatch, missing/extra/duplicate entries, traversal, forbidden types, checksum/size/padding faults, truncation/termination, resource caps, invalid receipt and abort. These tests demonstrate local parser behavior only, not a real encrypted archive, physical restore, PostgreSQL consistency or Supabase Storage behavior.
- The sampled manifest represents source observations before and after a non-atomic tar run. Equal observations cannot exclude intervening change-and-reversion; tar verification proves only that the captured *component's* files match those samples.
- `storage.objects` metadata is separately sampled as a row count and aggregate digest. The installed file backend can write object bytes before metadata commit and can delete files nontransactionally relative to PostgreSQL. The local contract does not provide a verified, row-by-row mapping from each database object/version to each archived file. Thus `metadataObjectMapping`, cross-store atomicity and a current rollback point remain **NOT_PROVEN**, even if this archive gate later passes. Four metadata rows and four files are not a mapping proof.
- No actual age identity, clipboard, source tar, encrypted backup or real restore was accessed in this unit. No DB/SQL, VM, service, provider, Git remote, Production or Home change occurred.

## Next qualification dependency

After a separately approved real component capture and independent owner-key verification, use this gate in an isolated restore environment on the decrypted Storage stream, then separately establish exact metadata-to-file/version correspondence and exercise a bounded physical restore. Do not promote the component to a combined atomic snapshot or claim current-state rollback without a cross-store consistency mechanism.
