## Supported mechanism and its limits

[Apple Virtualization.framework](https://developer.apple.com/documentation/virtualization/vzvirtualmachineconfiguration/networkdevices) exposes only network interfaces explicitly placed in `VZVirtualMachineConfiguration.networkDevices`; the default is an empty array. [Storage](https://developer.apple.com/documentation/virtualization/vzvirtualmachineconfiguration/storagedevices) can be restricted to explicitly configured file-backed virtual disks. The review-only `no-nic-synthetic-guest-vz-preflight.swift` constructs a configuration with zero network, directory-share, socket, serial, console, USB, graphics, keyboard and pointing devices, and exactly two read-only file-backed block devices (a RAW scratch boot candidate and a dedicated offline-input candidate). It calls `validate()` but contains no `VZVirtualMachine` creation or `start()`. It typechecks against the installed Apple SDK. This is **API-level feasibility**, not a runtime preboot NIC audit or a bootable guest.

The companion `no-nic-synthetic-guest-preflight.mjs` is a review-only design gate. It rejects Lima even with `networks: []`, an extra/missing device category or configuration field, non-RAW/original boot disk, any third disk, writable/network-backed/host-mounted input disk, extra or changed input identity, executable runtime state, and any real backup/Development/Production data fallback. It returns `guestBootAuthorized:false` even for an exact match. The existing owner-accepted unsigned-source gate and the old executable runner's null attestor/materializer gates remain unchanged.

## Why no boot was attempted

1. The installed `limactl` is 2.2.0. Lima's [default networking](https://lima-vm.io/docs/config/network/user/) exists even when the `networks` list is empty; the existing runner installs firewall rules only after guest startup. It cannot satisfy no-egress-from-preboot. The exact synthetic gate rejects this path.
2. The pinned Ubuntu input's 616,522,752-byte size matches the published [Ubuntu ARM64 release image](https://cloud-images.ubuntu.com/releases/noble/release/). Ubuntu's [QCOW image documentation](https://documentation.ubuntu.com/public-images/public-images-how-to/launch-qcow-with-qemu/) and Lima's [VZ conversion note](https://github.com/lima-vm/lima/issues/4056) indicate the distributed `.img` is QCOW2 while Apple's VZ file-backed disk requires RAW/ISO. **The exact local file header was not re-read in this unit**; even if it is the expected QCOW2 file, no verified isolated QCOW2→RAW conversion exists here. `qemu-img`, `qemu-system-aarch64` and `vfkit` were not found on the installed PATH/Homebrew Cellar; `hdiutil` is present but is not a qualified QCOW2 converter. No new download was authorized.
3. No dedicated offline disk containing exactly the two freshly rehashed QA files, no private writable scratch boot copy, no EFI/guest control and no read-back evidence disk were created. The Swift preflight attaches its two candidate disks read-only precisely so it cannot mutate input while reviewing configuration; a future actual runner needs a separately qualified writable **scratch** boot disk and an evidence/cleanup channel that is not a host mount or network.
4. A signed/entitled native VZ runtime, actual `validate()` against those exact scratch disks, pre-start device-list inspection, offline transfer verification, guest boot observations and secure rootfs materializer remain unqualified. A declared JavaScript plan or successful Swift typecheck cannot substitute for these measurements.

## Test and preservation result

Focused Node negative tests cover Lima-default-network rejection; hidden network/host share/socket/serial/forwarding and extra fields; disk count/RAW/original/transfer immutability; and real-data/runtime fallback. Swift typecheck passed using a temporary module cache outside the internal SSD home cache. No guest was started. No original database/backup, Colima, provider, `main`, Production, Home or Guard state changed. The exact next allowed engineering step is a **reviewed offline image staging/conversion helper** using only the two approved files and external scratch space, followed by a native VZ pre-start audit and guest-local runtime proof. Until that exists, synthetic QA restore and independent Development-backup restore remain **NOT RUN**.
