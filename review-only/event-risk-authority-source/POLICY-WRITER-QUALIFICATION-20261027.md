# Recipient/channel policy writer — isolated qualification only

## Scope and evidence

This unit adds `POLICY-WRITER-ISOLATED-NOT-APPLIED.sql` and `run-isolated-policy-writer-qa.mjs` under review-only. Direct SQL execution raises `DRAFT_NOT_APPLIED` before DDL; the file ends with `ROLLBACK`. The harness strips those two guards **only inside a new disposable PostgreSQL 17 container** (`--network none`, no host mounts, read-only root, tmpfs data). No existing Development or Production database, route, migration history, Supabase Auth record, Guard or provider was written. The harness stops/removes only its newly created container.

Duplicate-work check: local refs and `review-only/` contain a recipient-source sketch and a disconnected decision-time reader, but no qualified policy writer. Connected GitHub search for open PRs with “recipient policy” returned none; open Risk PRs #259/#260 concern effect plans/receipts and explicitly leave the authoritative recipient/settings producer unproven. The separate six-hour `automation-7` is a status summary, not a second implementation unit.

The draft mirrors the minimum columns and mutation shape of `digital_observer_authorized_recipients` and `observer_alert_channel_settings` for a **synthetic internal-profile toggle**. It does not copy or modify the deployed tables. The synthetic `site_authority_fixture`, `owner_session_fixture` and `site_member_fixture` stand for missing trusted sources and are **not** an approved authority system. In particular, a UUID supplied as `p_session_ref` is not a verified Supabase user session. A site/tenant/owner row inserted by the harness does not prove any historical Home ownership.

## Tested transaction contract

One function call locks an exact synthetic authority, owner session, policy head and relevant membership/current rows; rejects a wrong Tenant/Site, stale expected version, inactive/nonmember owner, ineligible recipient or setting, null-profile external recipient, or unknown channel/severity. It toggles exactly one existing internal recipient or channel setting, creates a sorted, data-minimal snapshot, inserts mandatory audit and immutable policy version, and CAS-advances the head in the same PostgreSQL transaction. No recipient address, delivery destination, provider reference, encrypted secret or raw profile is in the snapshot. The fingerprint is `sha256(jsonb::text)` **for isolated comparison only** and is not the canonical cross-language digest used by the separate decision plan.

The isolated test ran **41 PostgreSQL assertions**. It exercised guard abort; absent authority/session/head; expired/revoked session; owner membership; wrong Tenant/Site and target row; unknown eligibility; untrusted caller/direct-write denial; initial version and sorted snapshot; stale replay denial; setting change; immutable audit/history; mandatory-audit failure rolling back the current row, version and head; and two concurrent sessions where one commits and the other is rejected as stale. The separate `source-readiness-gate-v1.test.mjs` (8 checks) and existing `decision-time-producer-seam-v1.test.mjs` (18 checks) are relevant regressions. These are synthetic PostgreSQL and local contract results, **not** deployed Supabase Auth/RLS, actual current-route compatibility or live decision-time authority proof.

## Why activation remains blocked

| Missing fact | Evidence inspected | Exact consequence / future qualification |
| --- | --- | --- |
| Authoritative Home Site→Tenant→owner registration and immutable event-time acceptance | `SOURCE-BOUNDARY-20261027.md`, original Development catalog, and guarded ownership draft `a1089050` | The harness fixture cannot be mapped to real rows. Qualify the actual owner registration writer and acceptance transaction first; fail closed for null or ambiguous historical `observer_sites.digital_observer_organization_id`. Never backfill by current membership or organization. |
| Verified server-side caller/session provenance | Existing app access routes and synthetic `owner_session_fixture`; no new Auth connection was made | A caller-supplied session UUID is insufficient. Define a trusted, bounded Supabase session/role check (with revocation semantics) and verify role grants/Data API exposure before any privileged RPC. No `anon`, `authenticated` or `service_role` grant is proposed by this draft. |
| All current recipient/settings mutations in one serialization domain | `app/api/digital-observer/access-settings/route.ts` directly INSERTs/DELETEs recipients; `settings/route.ts` updates rows separately | The row/head lock does not prevent a direct writer from inserting a phantom. Every legitimate create/delete/toggle/settings path must be migrated to one qualified writer or blocked. This draft intentionally does **not** implement external-contact creation/deletion, global setting rows or contact-secret handling. |
| Real membership and eligibility for external contacts | `digital_observer_authorized_recipients.recipient_profile_id` is nullable; current route permits encrypted external destination; `recordEventNotifications` currently uses profile IDs for in-app entries | The candidate denies null-profile recipients rather than silently omitting them from an allegedly complete policy. External channels require a separate approved identity/eligibility and snapshot contract; no encrypted contact value belongs in the version record. |
| Decision-time/Risk binding, canonical digest and audit semantics | `decision-time-producer-seam-v1.mjs` is disconnected; plan authority is absent from Development; this audit is synthetic | Review an atomic producer binding event acceptance, persisted Risk and exact policy version/fingerprint. Define mandatory audit payload and failure/replay behavior against the real `immutable_audit_events` contract. No Risk, notification or Guard route was connected. |
| Retention, volume, indexes and cost | Only synthetic fixtures; no live usage estimate or approved retention | Policy versions and audit grow per authorized change. Data owner is the Digital Observer Tenant/Site; sensitivity is authorization/notification metadata. Before activation, establish legally approved retention, expected change volume, query pattern, index/cost forecast and recovery/rollback. **No retention policy is activated here.** |

`SECURITY DEFINER` is limited here to an isolated non-exposed schema and a non-login fixture owner with an empty `search_path`; it does **not** make a real deployment safe. Current [Supabase database-function guidance](https://supabase.com/docs/guides/database/functions) requires careful owner/search-path/EXECUTE treatment, and [RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security) distinguishes grants from row policies. A future version must be reviewed against the **actual** Supabase role/claim mechanism and qualified with caller-boundary tests. No migration is ready to apply.
