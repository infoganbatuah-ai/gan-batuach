## Write-path and commit-order map

| Path | Observed installed-code order | Backup implication |
| --- | --- | --- |
| Standard upload/upsert | `storage/backend/file.js:169-183` streams bytes and metadata sidecar to a versioned file; `storage/uploader.js:91-132,156-230` **then** upserts `storage.objects` in a DB transaction. Failure requests an `ObjectAdminDelete` job. | Bytes can exist before their metadata row. File and row are not one atomic transaction. |
| Delete / bulk delete | `storage/object.js:86-111,129-163` deletes metadata and invokes filesystem delete **inside** a DB transaction. | The filesystem removal cannot be rolled back with PostgreSQL; an in-flight operation can straddle a backup boundary. |
| Copy / move / upsert cleanup | `storage/object.js:297-349,425-509` copies bytes before destination metadata commit, then queues old-version deletion; `storage/uploader.js:188-230` similarly queues old-version deletion during completion. `storage/events/objects/object-admin-delete.js:29-65` removes files when a worker handles the job. | Old and new versions and queued cleanup can cross the DB/volume capture interval. A stable `storage.objects.version` alone does not guarantee its bytes remain until copied. |
| Resumable / multipart | `http/routes/tus/lifecycle.js:224-259` completes object metadata after backend bytes exist. `storage/backend/file.js:301-376` writes multipart parts under the file backend and assembles them before completion. | Pending/partial bytes are a separate state; simple volume copying may include incomplete data or miss metadata association. |
| Background jobs | `storage/events/workers.js:38-50` registers object-delete workers, but `start/server.js:102-110` starts them only if `pgQueueEnable`; `config.js:384` requires `PG_QUEUE_ENABLE` or `ENABLE_QUEUE_EVENTS` to equal `true`. Neither flag is present in this container configuration. | The queue mechanism is present; its worker is **not shown enabled by current config**. Do not claim active queued deletion from this observation, or assume a different/new worker can never run. |
| Direct writers outside Storage API | Catalog privileges permit `service_role` direct `storage.objects` DML despite RLS. Docker-admin/guest root can mount or alter the writable Storage volume as established in the preceding NO-GO. Repository paths such as `app/api/storage/upload/route.ts` and `app/api/documents/route.ts` call Storage API, while privileged scripts/routes could act independently. | Pausing only the Storage container does not fence privileged DB metadata changes or Docker-admin filesystem writes. Repository call sites are potential paths, not proof of live requests. |

The relevant relationship is **file bytes first → PostgreSQL metadata commit** for upload/copy, while delete can remove bytes within a DB transaction and TUS/multipart can leave pending parts. These are non-atomic cross-store transitions. Neither matching timestamps nor pre/post digests establishes that a running `pg_basebackup` and separately copied Storage files represent one consistent point.

## Storage-only GO/NO-GO

**NO-GO for a current-state, independently restorable combined backup with PostgreSQL live.** No supported, enforceable short barrier was found that simultaneously (1) prevents new Storage API writes, (2) drains all in-flight uploads/deletes and pending parts, (3) excludes privileged direct `storage.objects` writes, (4) excludes Docker-admin/root volume writes, and (5) keeps the file volume stable throughout a whole-cluster database backup. The prior source check established that the Docker daemon has no authorization plugin and current-account/guest-root access remains. A Storage-container pause could freeze a request mid-file-write or mid-DB transaction and would not constrain the other writer classes. No pause or access change was attempted.

PostgreSQL [documents](https://www.postgresql.org/docs/17/app-pgbasebackup.html) `pg_basebackup` as an online **whole-cluster** operation that starts with a source checkpoint and includes required WAL. It does not coordinate an external file-backend volume. Its replication/WAL and checkpoint effects are source actions, not read-only metadata inspection. The previously drafted **1 GiB cumulative encrypted output ceiling** and **3 GiB internal-free-space floor** remain conditional: old aggregate physical database/Storage measurements are not actual encrypted-byte bounds. A later authorized run would need a hard output guard, source-space/WAL checks, independent `age` recovery identity, and disjoint encrypted isolated restore with metadata/object reconciliation; none occurred here.

## Remaining fact and next gate

The missing control is a **provable cross-store consistency boundary**, not another static count: either a supported source mechanism that fences every privileged metadata and byte writer and drains outstanding operations for the entire online backup, or a verified transactional/version-retention method that preserves every DB-referenced byte version until copied and restored. The inspected local implementation/configuration supplies neither. Thus **do not start `pg_basebackup`, logical capture, volume copy, or restore on the theory that Storage pause alone is sufficient**. The next technical qualification must first propose and test such a mechanism in a separate isolated synthetic environment, then explicitly assess source checkpoint/WAL impact, 1 GiB/3 GiB limits and isolated restore before any original-source operation. No owner action is needed for this read-only NO-GO; any later source mutation or capture needs its own bounded gate.
