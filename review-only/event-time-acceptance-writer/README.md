## Actual source contract and narrow proposal

The canonical `observer_intelligence_signals` table and its `(source_type,source_id)` partial unique index come from `20260611003000_digital_observer_intelligence_network.sql`. `20260905010000_digital_observer_canonical_incidents.sql` installs an after-insert Signal→Incident correlation trigger and permits a nullable Incident Site. The active `app/api/video-gateway/cloud-events/route.ts` authenticates a Gateway and validates its current Site/Source, but inserts a Signal through a separate Data API transaction; it does not create an immutable event-time Tenant/Site acceptance. The proposed registration tables and `bind_accepted_event_v1` are on the unmerged source branch, not deployed.

`ACCEPT-LIVE-HOME-SIGNAL-NOT-APPLIED.sql` proposes one ungranted `SECURITY INVOKER` function that, in **one PostgreSQL statement/transaction**, serializes on registration identity and holds Source/Site/Tenant row locks through acceptance; accepts only a first-qualified, currently matched Home Source; inserts canonical Signal and requires a matching Incident link from the existing trigger; inserts immutable acceptance and mandatory ACCEPTED audit; calls the existing binding function, which adds BOUND audit. Any failure aborts Signal, Incident, receipt, binding, and audit together. A retry checks the full immutable JSON observation plus the persisted Signal, receipt, binding and audits before returning the original Signal ID. Existing receipt replay does not consult today's Site organization or current version. A colliding preexisting Signal without a receipt is denied, not backfilled.

The supported first-acceptance subset is intentionally narrow: `person_entered`, `line_crossing`, current version 1, source mode `live`, connected, active Home Site, enabled monitoring and consent, current organization/owner match, event time after qualification and within a 60-second live window. It accepts no transfer or old first-time backlog. The function does not take or process a claim owner nonce: claim acquisition and all four fenced writers remain disconnected. A stale claim owner cannot be authorized through this package.

The `p_observation` parameter mirrors the 13 immutable fields in `cloud-event-observation.ts`; extra/missing keys and payloads over 4 KiB fail closed. It is **not** a client API. A future server adapter must pass only the output of the existing Gateway authentication, event-validation and canonicalization pipeline. The SQL function independently checks registration, current Source, Site, Tenant and owner rows, but it cannot cryptographically establish Gateway authentication, device capture time, the legitimacy of a qualified registration version, or the identity of its future database caller from the supplied JSON. No role is granted EXECUTE or private-table access here.

## Blocking facts before any apply or active route change

1. **Registration authority:** the source proposal has no qualification writer. The existing `profiles.role`, Source `created_by`, organization label or caller-supplied registration row cannot prove a Home owner's authorization. Verify the exact owner/actor resolver, fresh session, audit provenance, and revocation before a trusted registration version can exist.
2. **Trusted server caller:** the existing server uses a Supabase service-role Data API client; this proposal is in a non-exposed schema, `SECURITY INVOKER`, with no EXECUTE/table grants. Granting broad table access to service_role would allow direct forged receipt insertion. A dedicated, narrowly scoped internal caller/privilege design and gateway-to-database authentication boundary are required. This proposal grants none.
3. **Event-time truth:** device-supplied `occurredAt` is not independently signed capture time. The 60-second/after-qualification restriction reduces but does not prove historical event-time authority. Old first-time backlog is denied. Cross-Site/Tenant transfer requires a separately qualified versioned, serialized cutover; current `source_id UNIQUE` registration identity cannot represent it. No transfer is simulated as safe.
4. **Signal/Incident integrity:** the source acceptance table's FK references only Signal ID; direct privileged insertion can still create a false cross-Site receipt. Future ACL, immutable Signal identity enforcement, canonical Incident-link constraints, and actual trigger/RLS/role-inheritance tests must ensure **all** writers and readers use the verified path. The active Risk claim still reads current Site organization and must not consume this proposal.
5. **Audit/retention/cost:** the review table's ACCEPTED/BOUND audit is not yet proven equivalent to the canonical immutable audit ledger. Data owner: Digital Observer Product/security; sensitivity: customer/source ownership and incident metadata; expected volume: one receipt+binding and two audit records per accepted entry event, plus versions; lookup by unique source key and Event ID. No raw media or credentials. Retention/legal hold and full storage/egress estimate remain unapproved; no deletion job is proposed.
6. **Deployment/recovery:** actual schema compatibility, permissions/Data API exposure, concurrent transfer, transaction crash recovery, and compatibility-first rollback still require a separately authorized isolated rehearsal. If stopped after future deployment, retain all accepted Signals, receipts, bindings and audit; do not drop or rewrite them to roll back. No migration, RLS/ACL change, or real database operation is included here.
