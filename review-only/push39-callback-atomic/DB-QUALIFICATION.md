# PUSH39 provider callback atomicity — review only

This directory is not a migration. `forward.sql` aborts before its candidate body. The QA runner strips that guard **in memory only** and installs the candidate solely in a newly named, disposable PostgreSQL database inside `digital-observer-pgqa-20261026`. Do not apply this proposal to canonical Development or Production, or connect the live callback route.

## Source contract and identified gap

- `app/api/digital-observer/provider-callbacks/route.ts` verifies a provider HMAC, callback key version, and an active Production provider before calling `applyAuthenticatedCallback`. The authenticated callback body is schema-limited. The proposed SQL does **not** verify the HMAC itself: it must be reachable only from that trusted server-side route with `service_role`, never from a browser or a caller supplying its own `signature_valid` flag.
- `lib/domain/digital-observer/notification-delivery-service.ts` inserts a row in `digital_observer_provider_callbacks` and then independently updates `digital_observer_notification_deliveries`. An update failure leaves a durable callback with the old delivery status. The existing replay path detects that mismatch and returns `CALLBACK_RECOVERY_REQUIRED`; it does not repair the pair.
- The candidate locks the exact delivery, validates provider/Site/channel, the decision-time `authorization_snapshot.profile_id` against a still-present recipient FK, and server role, identifies semantic replay, classifies terminal/ignored callbacks, then inserts the callback and updates delivery state in one database transaction. SQL errors roll both writes back. If a recipient was later deleted and its FK set null, the UUID-form decision snapshot retains the original recipient identity for recording historical provider evidence. `signature_valid=true` is only a record of the trusted route's prerequisite; it is not accepted as an RPC parameter or independent SQL proof of authenticity.
- An existing callback may legitimately be recorded without changing delivery status: an already terminal delivery, or a delivered delivery receiving an outcome other than acknowledgment. An identical replay returns the current status but does not claim the earlier callback performed a transition. A different callback with the same provider/event ID conflicts even across deliveries or Sites.
- The candidate mirrors `transitionForProviderOutcome` for callback-accepted outcomes: expired/cancelled/acknowledged/unknown/permanent failure, success→delivered, and bounded retry/dead-letter. It rejects nonterminal preconditions before inserting. `delivered→acknowledged` remains allowed only before expiry. Recipient/Site binding comes from the locked delivery; it does not authorize a new recipient or override the decision-time authorization snapshot. A callback documents the result of an already-sent delivery, so revocation of current recipient membership must not erase provider evidence.

## Synthetic qualification

`node review-only/push39-callback-atomic/run-isolated-postgres-qa.mjs --execute-disposable-qa`

The runner must verify the exact container is `NetworkMode=none`, has no mounts and no published ports, and that no prior database with its `do_p39_callback_qa_` prefix remains. It creates one database from `template0`, runs a reduced fixture with source-matched columns and real PostgreSQL roles, first proves the unchanged guard aborts, then tests the candidate only there. It drops only its own database in `finally` and verifies the matching catalog count is zero.

Covered: service-only EXECUTE; wrong provider/Site or recipient snapshot; callback after recipient FK deletion; success and equivalent replay; conflicting outcome, timestamp, and JSON; delivered→acknowledged; terminal evidence without regression; trigger-induced delivery update failure with full rollback; retry and ineligible status; missing/expired deadline; duplicate provider/event binding across deliveries/Sites; concurrent identical callbacks; concurrent conflicting outcomes; callback/delivery Site consistency.

This is PostgreSQL behavioral evidence on a **synthetic fixture**, not proof of current canonical schema, RLS, PostgREST/Data API exposure, historical data, provider HMAC delivery, Production configuration, or real provider concurrency. The isolated fixture omits active RLS, generated Supabase types, and installed service-role table grants. Those need separate authorized qualification before any migration proposal can be applied.

## Required future cutover gates (not authorized here)

1. Read-only preflight against verified canonical Development: exact deployed columns, status constraints, owner/grants, provider configuration, callback rows and delivery statuses. Reconcile every pre-existing callback from the legacy two-write path; otherwise the candidate's same-event replay could misclassify an orphan as atomic historical success. No historical rows may be silently deleted, overwritten, or backfilled without a reviewed recovery plan.
2. Review RPC exposure: `public` is PostgREST-exposed in the current architecture. Although the candidate revokes PUBLIC/`anon`/`authenticated` EXECUTE and requires `service_role`, a private, non-exposed schema should be preferred if the verified server client can reach it. Test actual role inheritance, RLS, Data API, and table grants. Restrict service-role invocation to the server callback route; any other server user of that role could otherwise forge an authenticated record.
3. Verify HMAC/key-version race behavior: the route validates the active provider before signature verification, while provider configuration could change before SQL commit. Define and test the required revocation/rotation cutover (including whether locking the provider configuration row is needed). No RPC parameter can replace independent signature verification.
4. Validate callback outcome and status parity against canonical migrations, including every `sent`, `delivered`, terminal, retry, and expiry branch, plus original recipient/Site authorization snapshot. Decide whether `digital_observer_action_audit` needs a mandatory transaction-coupled record beyond the callback evidence row. The candidate does not create a separate action-audit row.
5. The **dispatch** path remains a separate atomicity gap: `dispatchQueuedDelivery` inserts a delivery attempt, then updates delivery state in another operation. Its failure and external-provider unknown-outcome windows are not fixed by this callback candidate; do not claim PUSH39 delivery atomicity complete.
6. Only after an authorized Development migration, isolated canonical integration tests, recovery plan, and exact-head CI may the active route be changed to call an installed RPC. Then verify no historical orphan, return-shape compatibility, and real signed callback tests. No provider activation is included.

Rollback before active-route cutover: leave the guarded proposal unapplied. After a future additive installation but before cutover, revoke its EXECUTE and retain existing records; do not drop historical callback/delivery rows. With active traffic, first disable provider callback ingress and reconcile in-flight events before any function replacement or rollback. No lossless rollback is claimed until rehearsed against the canonical schema.
