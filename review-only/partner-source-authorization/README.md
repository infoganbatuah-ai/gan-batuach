# Partner service-account source authorization

**Source-only authorization is blocked.** The checked contracts authorize Sites, including delegated customer Sites. There is no authoritative source grant for a partner service account or embedded session in the inspected paths. Continue using existing Site-scoped access under the current contract. Issuing that access cannot satisfy a request for one-camera isolation.

## Minimal proposal

Introduce an explicit server-side resource scope for service accounts, with existing accounts retaining their existing Site behavior. A new source-restricted account must enter that mode before it can be issued or used. The account and its first grant must become effective atomically. Missing scope state, grant lookup error, a missing grant or an empty restricted set denies access. Never fall back to Site access in source-restricted mode. Keep the initial contract to one camera and explicitly granted read operations.

An authoritative grant needs an immutable grant ID, the service-account ID, delegated partner customer ID when applicable, canonical customer Tenant and Site, canonical camera-source ID, ownership generation, allowed operations, issuance and expiry, revocation state and sanitized issuer audit reference. The issuance operation must prove the issuer can delegate that exact capability for that customer, Site and source and enforce the one-camera constraint transactionally. Partner account creation, a requested camera ID or a package entitlement alone cannot authorize issuance. Keep grants private to the scoped registrar and enforcement readers. Store no stream URL, channel alias, provider credentials, archive locator or footage.

On every use, intersect current account permission and Site authorization with the exact current source ownership and an active grant. Recheck partner-to-customer and customer-to-Site bindings when applicable. A trusted ownership change must invalidate the grant atomically or advance a durable ownership generation. Reassignment away and back must not revive a previously issued grant. A source deletion, missing ownership, ambiguous legacy identity or replacement source also denies access. Revocation remains visible in audit history. Verify migration compatibility and all ownership writers before choosing a generation field or revocation mechanism.

## Enforcement placement

See the [route-by-route enforcement matrix](route-enforcement-matrix.md) for lists, detail lookups, aggregates and links.

- **External v1.** Preserve request signing, receipt, entitlement and Site authorization. Resolve effective resource scope after these checks, before any source-derived query or signing operation. The first qualified restricted surface should be camera inventory/detail and health using a server-derived exact source filter in the query before limit and pagination. A request filter can further narrow those results. Any route whose result cannot be proven to contain only the granted source stays closed for restricted principals.
- **Events, metadata and Investigation.** When separately qualified, authorize each resource by its server-resolved canonical source, including ID lookups. Deny unresolved provenance, cross-source Incidents and derived results or counts containing a second source. Apply the same boundary to investigation candidates, cross-camera summaries, Watch Rules, webhook dispatch and generated links before enabling those operations for a restricted principal.
- **Evidence and archive.** Authorize Evidence and its canonical Event/source before revealing a reference or attempting a media operation. Issuing a durable bearer URL would create a separate revocation exposure. Keep media and archive unavailable to a restricted principal until retrieval and per-use revocation are qualified. No archive route is proposed here.
- **Browser embedding.** Bind newly issued restricted sessions to the authoritative restricted account and grant. A session cannot expand the issuer's scope. Check the grant and source ownership on dashboard reads while preserving audience, Origin, expiry and current Site checks. Until the binding and filtered aggregation are qualified, deny issuing an ordinary Site-wide token through a restricted account. Existing Site-scoped sessions continue under their existing contract.
- **SDK.** Keep query options as selectors. Preserve existing contract versions and methods. The API owns the grant decision, regardless of SDK, missing filter, pagination, hand-written request or cached identifiers.

**Proposed owner boundary.** A fresh authenticated customer-side actor must have independently verified delegation authority for the current Tenant, Site and source, and give explicit approval for the recipient account, operations and expiry. The registrar proves the existing partner relationship and recipient scope and binds the current ownership versions in the same transaction as issuance and mandatory audit. The verified customer issuer, an independently authorized scoped revoker, or a canonical ownership transition can revoke. The recipient, partner-control identity, generic Management roles and recorder credentials must receive no issuance or self-approval authority.

**Proposed write fence.** Track monotonic Site and source ownership versions, or prove a transactional permanent revocation mechanism covering every write path. Increment the Site version for an authoritative Tenant/ownership change and the source version for a Site, source identity or qualifying physical rebinding change. A return to earlier IDs cannot restore an older version. Use the same guarded read in issuance and authorization, and never reset versions on restoration in a way that admits stale grants. Prefer a database-enforced write boundary over adding independent best-effort invalidations to individual HTTP handlers. Source moves, tenant moves, administrative updates and physical rebinding remain blocked for grant activation until that boundary and rollback are qualified.

## Qualification gate

The new focused test exercises the current signed SDK and route with a synthetic database. A delegated account filters the camera list to one camera and still reads the sibling camera's Evidence metadata on its authorized Site. Removing the customer–Site link denies the same read. This demonstrates the existing Site contract. It supplies no source-grant proof.

Before issuing a source grant, qualify a separately authorized Development migration and confirm the deployed source ownership writer, historical Tenant/Site provenance and issuer authority. Test one-source list/detail/health with no filter and with the sibling filter, direct ID and derived-resource denial, absent and revoked grants, Site/customer/tenant transfer and return, stale or expired account and session, disabled operations, and no broad fallback on errors. Validate ACLs and Data API exposure. Exercise concurrent revocation and lookup before any media consideration. Roll back by disabling restricted credential use while retaining grant and audit history. Preserve existing Site credentials.

`node --test scripts/qa/check-partner-source-authorization-model.mjs` checks the proposed invariant with synthetic records only. It exercises Site and source transfer from A to B and back, stale issuer approval after return, matching new approval, explicit revocation, the exact expiry boundary and preservation of ordinary Site access. It does not exercise a database, live issuer, product write fence or production grant.
