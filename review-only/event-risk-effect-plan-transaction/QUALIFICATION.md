## Exact proposed transaction

The function accepts only an `authority_id` in caller JSON, requires `service_role`, and locks the canonical Signal → Site → organization → Event link → Incident → claim sequence. It verifies the current nonce, monotonically increasing epoch, unexpired lease, `RISK_PERSISTED`/`EFFECTS_PENDING`, Model A scope, actual Risk row and the proposed first-writer persistence receipt. A **separate, immutable, server-produced** authority row must bind the exact claim/Risk/Tenant/Site/camera/Incident, decision-time recipients/settings/policy/evidence and all expected effect fingerprints. The worker, client, current mutable settings and email address cannot create that authority.

The proposed transaction derives the required effect keys from the same inventory as `event-risk-recovery.ts`, validates an exact versioned snapshot, then inserts the frozen plan, mandatory audit and fenced `EFFECTS_PENDING` checkpoint atomically. Failure of audit or the final fenced update aborts all three. Replay under a *current* owner compares the complete immutable semantic plan and linked audit; conflicting settings, recipients, expected effect fingerprints or scope fail rather than overwrite. Guard eligibility is only a durable effect key, never a command or external acknowledgment. This function does not record effects or mark processing complete.

The proposed authority and plan tables are **new objects**, not deployed catalog facts. The authority producer is absent. Both tables enable RLS and revoke all default rights from `PUBLIC`, `anon`, `authenticated`, `service_role`; the exact function revokes default EXECUTE from all four. Synthetic fixture-only grants permit isolated testing. A future migration needs a separately reviewed, least-privilege authority writer and exact grants, Data API exposure review, retention, and immutable-row enforcement. `SECURITY INVOKER` and `search_path = pg_catalog, pg_temp` avoid a public `SECURITY DEFINER` surface. Supabase's default public-object grants make explicit revocation necessary [source](https://supabase.com/docs/guides/api/securing-your-api).

## Digest compatibility gate

The current TypeScript `createDecisionTimeRecipientSnapshot` fingerprints `JSON.stringify` of a locale-sorted object. PostgreSQL `jsonb::text` is a different serialization. This proposal names its database-only digest algorithm `pg-jsonb-text-v1` and tests byte-identical round-trip of that serialization. **It does not assert compatibility with the TypeScript fingerprint.** A future producer/reader must implement and version one verified cross-language canonical encoding before this function can be installed. The proposal also uses PostgreSQL `C` ordering in validation, which may differ from JavaScript `localeCompare` for non-ASCII references; this is another explicit compatibility gate, not a silent normalization.
