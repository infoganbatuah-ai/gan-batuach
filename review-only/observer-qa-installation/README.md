### Staging and origin review

The mounted POST stays closed by default. A single approved Preview deployment can read a new or revoked operator window on each request without a per-window environment change. The flag, pinned project and Preview-only service credential are deployment settings. No deployment or setting changed in this qualification.

The original Product RPC requires both a live, verified user session and the private, five-minute server ticket. Keep that requirement. ECDSA signature verification is performed in Next, so the database needs evidence of the server's participation before recording proved_at. It checks the independent ticket digest, actor, bound session, key, Site, source, nonce, expiry and revocation under its row lock. Direct authenticated calls without a valid server ticket cannot mark proof. The new service-role RPC is read-only; this candidate does not move consumption into a service-role write path.

The existing SQL operator independently verifies the actor, Site/source and public-key pin. The private stage_window function generates the existing window ticket in the database, stores its hash in the qualified window and stores its encrypted value in the existing Supabase Vault in one transaction. A private slot links the exact operator-created Vault ID to the request. No new long-lived key or provider is needed. The close_window operation revokes the row and deletes only that slot's ticket in one transaction. Expired and completed windows are immediately unreadable. The operator must still run close_window to clear encrypted material after expiry or completion. Receipt and audit timestamps remain in the base table. [Supabase Vault](https://supabase.com/docs/guides/database/vault)

The Next server checks the deployment, request origin and authenticated Product user before reading. It calls only the fixed project URL and argument-free reader RPC with its server credential. The separate Product RPC receives the user's verified bearer and a scoped ticket. Neither credential enters an app response. The database returns a private envelope only for exactly one eligible, correctly paired window. Zero, multiple, expired, revoked and missing Vault entries fail closed. The function responsible for decryption is a fixed, argument-free SELECT owned by the trusted staging operator. The reader has no arbitrary Vault decryption permission. The existing service credential itself has broader project privileges: this change restricts how this code uses it, not the key's platform-wide authority.

The existing first-party QA proxy admits an owner to a temporary window, strips its admission cookie and forwards Product cookies to a loopback-only Next process. It explicitly rejects a remote Observer upstream. This does not prove Vercel SSO, proxy identity, Host/HTTPS forwarding or Secure/HttpOnly cookie renewal for the actual Preview. Do not reconnect that proxy to Vercel or bypass SSO. Verify provider redaction of request bodies and database parameters before an external window. The raw Preview host fails the exact origin check. Previously issued client cookies may require reissuance.

The server independently verifies the Product session, scope, signature and one-use decision. Its reply remains PENDING and grants no viewing permission. The QA-only native signing method reads the existing installation tag and key, compares SPKI and signs the domain-separated nonce. It cannot create or replace a missing key. No WebView bridge or UI invokes it in this candidate. Before physical qualification, separately review the exact main-frame origin and native request/return binding and confirm the installed app has retained the matching installation key. Device possession and hosted association are open.

## Rollout decision

**GO for source and database-security review of the staging reader. NO GO for hosted SQL, external ingress, deployment or device qualification.** q669 used the already installed Supabase Vault 0.3.1 and pgcrypto 1.3. The same PostgREST process observed operator staging and revocation. Authenticated and anonymous reader access was denied, ambiguity and TTL failed closed, and a real authenticated session could not consume with a known nonce and a missing or incorrect ticket. Zero proof timestamps were recorded. The local Next transport tests used doubles to check credential destinations and client responses. They do not establish hosted or physical proof.

Before any hosted GO, independently confirm existing Vault/pgcrypto and their permissions and operational cost, genuine Preview-only service credential and pinned target, least-privilege operator access, Site/source ownership, log redaction, tested external HTTPS/SSO/cookie boundary and native signing authorization. No hosted catalog or credential was accessed here.

Future authorized migration order: review the target catalog, apply the isolated enrollment forward transaction, then the reader forward transaction. Only the trusted operator may stage a bounded row. After testing, close the exact request and remove its Vault material, close the route, and apply reader-rollback.sql **before** rollback.sql. Reader rollback removes the dedicated API surface and ticket slots, preserving the base proof receipts. The base rollback removes its dedicated privileges and retains receipts. Keep the separate Site SQL guarded, its caller disabled outside q669, and its Site, receipt and audit rows intact.
