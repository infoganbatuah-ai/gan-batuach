# Push 42 source recording linkage review

**Trusted lookup is blocked.** The checked branch records Event-to-Evidence provenance and source recording references independently. It does not establish that a particular archive recording contains the material represented by an Event and its Evidence. The audited range adapter still has no production lookup. This review describes a proposed migration in prose. It includes no SQL, schema change or runtime activation.

### Requests that must stay unavailable

- One archive overlaps the Event, including an exact interval match, but no verified association exists.
- Two recordings overlap a requested interval. Selecting the most recent row or the closest start time would substitute guesswork for evidence.
- The Event camera resolves only through a legacy stream alias or the historical Tenant ownership is ambiguous.
- A client, report, external SDK, or mutable JSON field supplies the purported link.
- The Site, source, Event, Evidence, retention or trusted archive identity changes after the association was registered.

## Proposed additive migration for manager review

1. **Confirm dependencies.** In separately authorized isolated Development, compare deployed catalog to the archived schema. Verify current Tenant lineage, source uniqueness and lifecycle, supported Evidence rows and revocation/retention behavior, default privileges, schema exposure and all current reference consumers. Obtain the recovery handoff and a trusted recorder identity/clock and archive provenance contract for one approved source. Verify that it can positively identify a source-owned recording and establish the Event/Evidence association. If any proof is missing, keep the link absent.
2. **Use one server-only association.** Proposed working name `observer_source_recording_evidence_links`. The first increment needs one authoritative link per Evidence ID. Store the recording reference UUID, the canonical signal UUID, the Evidence UUID, Tenant/Site/source scope, link version, verifier operation ID, verification time, optional revocation time and reason code, and a server-derived digest of the verified association. Store no provider locator, URL, credential or footage in the link. Reference existing rows with real FKs. Preserve existing retention and cleanup behavior by allowing dependent links to disappear when a referenced row is permanently deleted. Preserve only the existing sanitized audit history after deletion. A revoked association remains ineligible for reads. An equivalent registration retry is idempotent. A conflicting registration fails closed and is auditable, with no silent replacement.
3. **Bind scope atomically at write and read.** Only the trusted server registrar may write through an isolated, non-exposed surface and explicit privileges. In the same registration transaction, lock and verify the recording, Event, Evidence, Site, source and authoritative owner binding. Confirm that the clip references the exact signal and source, that all rows belong to the same Site and Tenant, and that source and verified channel match the trusted recorder receipt. Use the established Event observed time, independently checked recorder clock and verified overlap. Revalidate current ownership, links, media policy, retention, revocation and exact full range coverage in one consistent trusted lookup before returning the existing `RecordingLink` shape. Ownership changes, row mutations or ambiguous matches must not resurrect the link. Maintain fresh Server session, `recordings.view` or equivalent reviewed archive authorization, `evidence.view`, investigation entitlement, history privacy and exact source grant. Link validation cannot substitute for those gates.
4. **Keep the locator private.** No PUBLIC, anon or authenticated access to the association. Use explicit schema and object grants for the authorized registrar and reader. Review the existing reference table's user-facing fields and ensure raw locators remain in server custody. Ordinary Event/Evidence/SDK payloads expose no archive locator. Keep recognized canonical Event and Evidence IDs distinct from provider IDs in the append-only audit. Validate exact grants and the negative role matrix before account or source enrollment.
5. **Qualify before enabling.** First test isolated synthetic DB cases for absent, conflicting and replayed links, wrong Tenant/Site/source/Event/Evidence, expired ranges and retention, ambiguous legacy mappings, unauthorized insert/read, concurrent changes, deletion/revocation, missing app scope, and audit acknowledgment. No historical time-based backfill. The first real link requires separate authorization and archive proof after camera recovery. Keep private transport and playback unavailable until the link, bounded range delivery and audit have separate evidence.
6. **Rollback without losing canonical data.** Disable the registrar and reader and keep the fail-closed result through the existing adapter boundary. Do not remove recorder content, Event/Evidence rows, recording references, or audit records. Keep protected association history through the applicable retention period. Asset deletion and proof of safe schema reversal must be reviewed separately. No destructive rollback is proposed.

**Not run:** SQL, catalog reads, RLS or ACL execution, archive lookup, partner connectivity, live media and recorded playback. The schema conclusion is based on checked source and archived DDL. The disconnected proof qualification below does not change that conclusion.

## Local Development availability and proof fixture

On November 27, 2026, `colima list` reported the canonical `gbi` profile stopped. The configured `colima-gbi` Docker context pointed to a missing Unix socket and the server probe failed. Loopback listeners in the local development port range were SSH processes, which did not establish the identity or isolation of a database behind them. No connection to those ports, VM start, SQL, or catalog query was performed. Deployed grants and RLS remain unverified.

The disconnected verifier in [source-recording-proof.ts](../../lib/domain/digital-observer/source-recording-proof.ts) defines a proposed receipt for a future trusted archive verifier. The payload is strict, flat JSON encoded as UTF-8 with its ASCII keys sorted. The Ed25519 public key is supplied by trusted server configuration. The expected operation, owner scope, recorder, physical channel binding, checked clock epoch, exact Event and Evidence IDs, recording-reference UUID and independently established anchor digest must also come from the trusted registration context. A receipt binds the exact requested range and expires within two minutes.

The clock model uses signed integer millisecond values. Recorder offset means recorder time minus UTC. The signed clock verification interval must cover both possible archive edges for the same clock epoch. The requested interval must fit inside the guaranteed overlap after subtracting uncertainty at both ends, include the Event and be at most five minutes. The first fixture policy accepts up to two seconds of uncertainty and an offset of at most two minutes in either direction. These are proposal limits exercised by the synthetic qualification, not measurements from a recorder.

A real issuer must prove that an actual anchor from the archive matches the independently verified Event/Evidence anchor and that the archive epoch is covered by measured clock evidence. The local relay's time of observation or a signature over a guessed association cannot supply that proof. Durable one-use operation consumption, authoritative recorder enrollment and canonical link persistence remain prerequisites. The verifier has no production caller, key custody, playback or transport and returns no archive locator or media. Run `node --experimental-strip-types --test scripts/qa/check-source-recording-proof.mjs` for the synthetic cases.
