## Narrow effect and target

Only `EVENT_INCIDENT_LINK` is modeled. The canonical target is the existing `public.observer_correlated_event_links` row, created by the Incident correlation path, with `source_type='observer_intelligence_signal'`, exact Signal ID, Site and Incident. Its `id uuid` and relevant columns come from `20260606003000_multi_camera_correlation_engine.sql:39-67` and the canonical source type plus one-signal index from `20260905010000_digital_observer_canonical_incidents.sql:23-32`. The function **verifies** this already-committed row under a lock; it does not create a link or invent an Incident. Missing or changed target fails closed. No notification, provider delivery, physical action, Guard execution or other effect is implied. All other effect keys raise `EFFECT_UNSUPPORTED`.

The proposal adds the source-inventory receipt PK `(signal_id,risk_engine_version,effect_key)` and proposed deltas `target_link_id`, full-target-row digest + version, and mandatory audit ID. The target row's `to_jsonb(row)::text` is SHA-256 hashed as `pg-link-jsonb-v1`, then compared to both the caller precondition and the previously frozen plan fingerprint. This is a **PostgreSQL-specific** versioned encoding, not proof that the TypeScript producer computes the same digest. Every retry rereads the actual link and checks receipt scope, Risk, owner epoch, target ID/digest and linked audit metadata. A new owner can reuse an identical old-epoch receipt; an expired or stale owner cannot. The proposal does not set the claim to `COMPLETED`.

## Transaction and authorization

The exact lock order follows the preceding proposals: Signal → Site → organization → link → Incident → claim → Risk → plan → receipt. The function checks the current owner nonce, monotonically increasing epoch, live lease and `EFFECTS_PENDING`, then revalidates Model A Tenant/Site/camera/Event/Incident/Risk scope, the proposed authority row and plan audit. It inserts mandatory audit and one receipt in the same PostgreSQL transaction. Audit failure rolls back the receipt; unique receipt PK serializes same-key attempts after the claim lock. No external call occurs in the lock window.

**Critical blocker, positively demonstrated:** `SECURITY INVOKER` needs direct `INSERT` on the proposed receipt and audit tables for `service_role`. In the disposable fixture, that role directly forged matching audit+receipt rows, then the RPC accepted them as replay (`reused=true`) without executing its first-write path. The entire demonstration was rolled back. A future installation must use an independently reviewed dedicated non-exposed privileged writer/definer boundary with exact grants and Data API review, or another mechanism that prevents direct table mutation. A mere function `EXECUTE` restriction does not close this gap. The SQL grants no role any new access; it begins with an aborting guard, enables RLS on the proposed receipt and revokes default `PUBLIC`/`anon`/`authenticated`/`service_role` privileges. Existing target-table ACLs were not changed.
