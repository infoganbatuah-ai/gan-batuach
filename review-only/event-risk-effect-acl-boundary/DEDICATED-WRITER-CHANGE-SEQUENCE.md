## Transport and identity boundary

The candidate is **one direct PostgreSQL server-side call path for this one effect RPC**, not a replacement for `lib/supabase/admin.ts`. A new LOGIN role `do_effect_executor` would authenticate from the server process through a supported loopback/TLS-verified or approved pooler connection; a separate NOLOGIN, NOINHERIT `do_effect_writer` would own only the reviewed function and have exact table rights. `do_effect_executor` must not be a member of `do_effect_writer`, `service_role`, `postgres`, or another role with audit/receipt writes. The function must validate the fixed `session_user` of the direct connection, exact function arguments and Model A Tenant/Site/claim fences. PostgREST's `authenticator` session cannot be treated as this direct login and must not receive the new role or function privilege. If actual pooler/auth behavior does not preserve the expected `session_user`, **stop**; do not weaken the guard or substitute an unsigned header/`SET ROLE`.

Proposed server-only configuration names (not created; **no values**): `OBSERVER_EVENT_RISK_PG_URL` (secret connection locator, not `NEXT_PUBLIC_`), `OBSERVER_EVENT_RISK_PG_TLS_CA` or approved verified trust configuration, `OBSERVER_EVENT_RISK_PG_POOL_MAX` (small hard cap), `OBSERVER_EVENT_RISK_PG_CONNECT_TIMEOUT_MS`, `OBSERVER_EVENT_RISK_PG_STATEMENT_TIMEOUT_MS`, and `OBSERVER_EVENT_RISK_EFFECT_WRITER_ENABLED` (default `false`). Secrets must live in an approved server secret store, not Git/client/CI logs. A new role/secret/transport and any metered connection require separate owner authorization, provider compatibility and ₪15/user preflight; a zero fixed cost is **not** assumed. No new outbound network access or Production fallback is allowed.
