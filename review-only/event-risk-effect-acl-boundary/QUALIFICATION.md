## Candidate boundary tested in isolation

The narrow candidate **requires a new, independently authenticated direct PostgreSQL server transport**. It cannot be silently substituted into the current Supabase-JS/Data API path.

| Principal | Function | Audit / receipt tables | Other source tables |
| --- | --- | --- | --- |
| `do_effect_executor` | Exact seven-argument `record_event_risk_effect_v1` EXECUTE | No SELECT/INSERT/UPDATE/DELETE | No direct grants |
| `do_effect_writer` | NOLOGIN, NOINHERIT, sole SECURITY DEFINER owner | SELECT+INSERT, no UPDATE/DELETE; receipt RLS policies narrowly scoped | SELECT on exact required tables; `UPDATE(id)` or `UPDATE(signal_id)` solely for row locks |
| `anon`, `authenticated`, `service_role`, PUBLIC | No EXECUTE | No proposed receipt grants | Existing rights **unchanged** |

The test loads the **actual guarded local candidate SQL**, after proving its guard aborts, into a new disposable fixture. The candidate copies the PR #260 seven-argument body with only the reviewed security-mode, caller-identity and audit-actor changes: `SECURITY DEFINER`, `session_user = do_effect_executor`, and audit actor `do_effect_writer`. A direct PostgreSQL login retains that `session_user` under a definer; `current_user` becomes the NOLOGIN function owner and cannot authenticate the caller. A PostgREST request normally runs under the `authenticator` session and is intentionally **not** qualified by this guard. The writer role has no LOGIN, the executor is not a member of it, and the function keeps `search_path=pg_catalog,pg_temp` with fully qualified table references. A future function creation and all exact grants/revokes would have to be one reviewed transaction so there is no PUBLIC-execute window. PostgreSQL's [session-user](https://www.postgresql.org/docs/17/functions-info.html) and [function security](https://www.postgresql.org/docs/17/sql-createfunction.html) rules govern this pattern; merely flipping an existing public function to SECURITY DEFINER is unsafe without this entire boundary.

The public schema remains source-compatible for the exact RPC name, but the executor is **not** an API role configured for PostgREST. A public-schema function may still be discoverable; exact EXECUTE revocation is essential. This is not proof of actual PostgREST cache behavior, network isolation, managed-role inheritance, or a supported new server credential. Do not expose `do_effect_executor` through the Data API, use `SET ROLE` as an authorization signal, or put its credential in a client bundle. A future transport would need secure server-only custody, connection limits, pooler compatibility, secret rotation, and an exact caller migration reviewed separately.

It first verifies both review SQL guards abort, then removes the candidate guard only in the disposable fixture. It verifies: the executor can call the actual candidate function; target+audit+receipt are atomic; replay is idempotent; stale nonce/epoch and expired lease are fenced; cross-Tenant and cross-Site claims are rejected; a forced mandatory-audit failure leaves no effect receipt; direct audit and receipt SELECT/INSERT/UPDATE/DELETE are denied; forged audit+receipt cannot be submitted by executor; the function owner is NOLOGIN/NOINHERIT; `SET ROLE` escalation is denied; anon/authenticated/service_role calls are denied; even a deliberately accidental PUBLIC EXECUTE grant is rejected by the direct-login guard and then revoked; exact EXECUTE revocation stops subsequent calls. It also positively confirms `service_role` retains direct audit INSERT in the synthetic representation of the current broad path, but a combined forged audit+receipt transaction fails on receipt privilege and rolls back the audit. No existing database, clone, route or provider was touched.

The unchanged original `event-risk-effect-receipt-transaction/run-isolated-postgres-qa.mjs` also passed **27** synthetic receipt-contract checks. The new test statically compares the candidate's complete function body with PR #260's guarded body and permits only the three declared security/actor substitutions; it rejects an audit-table revoke in the candidate. Both test suites use disposable PostgreSQL only.

The synthetic fixture does **not** reproduce the actual Supabase role hierarchy, existing audit RLS policy, PostgREST/Data API configuration or cache, default grants, pooler `session_user`, full audit hash trigger, deployment permissions, external jobs/clients or historical ownership. Its permissive audit-writer RLS policy exists only in the disposable fixture; the guarded candidate does not change existing audit policies. It proves a PostgreSQL ACL pattern, not a deployed security boundary.

## Fail-closed decision and next gate

**Current server path: BLOCKED.** `createAdminClient()` authenticates as broad `service_role`; direct audit INSERT remains available and the candidate's `session_user` check deliberately rejects that Data API session. No grant to `service_role` or global revocation of existing audit rights is safe from the available evidence. A privilege-only change inside PR #260 cannot satisfy both function execution and no direct audit/receipt writes on the current route.

**Potential future path:** obtain explicit approval for a dedicated server-only PostgreSQL connection identity and a separately reviewed isolated Development privilege migration/route adapter. First inventory all audit writers and actual managed grants/default ACLs with authorized read-only catalog evidence, then rehearse exact role inheritance, RLS, Data API denial, function owner, wrapper grants, rollback and provider/pooler support against a separately authorized isolated Development environment. If that cannot be proven, keep the third writer uninstalled and leave the event-risk route/Guard inactive. No paid service, credential or Production action is implied by this proposal.

**Rollback proposal, untested live:** revoke executor EXECUTE first and stop its route; preserve all canonical target/audit/receipt rows; only then restore the previous server adapter. Do not drop nonempty claim/receipt/audit tables or delete evidence. The isolated test verifies EXECUTE revocation, not a lossless deployment rollback.
