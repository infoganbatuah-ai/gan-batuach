# PR #235 — private Legacy compare executor, pre-activation package

Status: **isolated implementation complete; Production deployment BLOCKED**. Scope is the existing Home Gateway and Connector only. No Production credential, verifier, Keychain value, device service or row was read or changed for this implementation. Both real matches remain **UNKNOWN**. The only permitted comparison output is `MATCH`, `MISMATCH`, or `UNKNOWN`.

Final access-decision and approval boundary: `DIGITAL_OBSERVER_HOME_LEGACY_PRODUCTION_ACCESS_APPROVAL_PACKAGE_20261021.md`. The package preserves this implementation but does not claim that its Product-side/private database capability or immutable Production audit sink exists.

## Implemented boundary

`home-legacy-private-executor.mjs` composes the existing administrator approval store/coordinator and the existing constant-time Legacy comparator; it does not implement another comparison algorithm. It exports one in-process `compare` operation. It opens no HTTP listener, database connection or Keychain item. It rejects extra input fields and devices outside the two pinned Production enrollment bindings. The approval store enforces authenticated platform-admin identity, exact device/tenant/Site, explicit purpose, at most five minutes, two atomic attempts per approval, replay denial, revocation and append-only redacted audit. The scoped reader has a fixed SQL predicate for exact enrollment ID, device ID, tenant ID, Site ID, profile, config version, active state and Legacy scheme, and returns only a status to the executor.

`home-legacy-keychain-source.mjs` is a read-only adapter for the existing macOS Keychain store contract. It selects the Gateway or Connector namespace supplied by a trusted operator, verifies the stored device and Site IDs, rejects an Ed25519/QA identity and non-Production cloud destination **before** reading `device_refresh_token`. It never writes, removes, rotates or caches credentials. No Production Keychain namespace is wired by this package. JavaScript strings cannot be reliably zeroized; a future activation must keep the process short-lived, disable request-body/error logging, avoid crash dumps, and prevent secret values in environment variables, argv, files or audit. The local Keychain access-control prompt and recovery procedure are still live gates.

The isolated E2E suite uses synthetic Gateway/Connector credentials, exact-shaped enrollment records in PGlite, an isolated approval SQLite file and in-memory Keychain stand-ins. It covers success, mismatch, wrong tenant/Site/device/enrollment, wrong local identity/destination, expiry, replay, attempt ceiling, revocation, no verifier result, and unchanged enrollment rows. It does **not** prove Production credential match, a real administrator session, actual Keychain access, or a real Production deployment.

## Production privilege audit and blocker

Read-only Production catalog checks on 2026-10-21 found `public.video_gateway_device_enrollments` has RLS enabled and one `is_admin()` policy. `anon`, `authenticated`, `service_role` and `postgres` have table `SELECT` privilege; `service_role` and `postgres` bypass RLS. All four roles have `public` schema USAGE and can execute `notify_role` and `process_monthly_inspection_reminders`; both are writable SECURITY DEFINER functions with no independent caller check. The prior review identified 57 PUBLIC-executable functions, five directly callable writable SECURITY DEFINER functions. A new `NOLOGIN` or `NOINHERIT` role would still inherit `PUBLIC` function EXECUTE, so **it is not an isolated Production reader**. The withdrawn draft migration is a no-op and must not be treated as a permission fix.

**Required executor privilege: none at the database or network layer.** It should receive only a bound `compareBoundCredential` capability and an approval-store capability. A future trusted Product-side data broker would need `SELECT` on exactly the ten named enrollment columns for the two fixed rows, and no device write/refresh/enrollment permission. With current grants, that narrow capability is not enforceable solely by adding a role: an existing `service_role`/`postgres` session has wider table and function rights, and any new role sees PUBLIC EXECUTE unless those grants are separately corrected. A hard-coded SQL query and module boundary reduce accidental access but do **not** remove the underlying privilege-escalation risk if the broker is compromised. No unrestricted service-role token may be supplied as the executor interface or placed on the Home device.

The five-function ACL proposal in `DIGITAL_OBSERVER_HOME_PUBLIC_FUNCTION_REMEDIATION_PROPOSAL_20261021.sql` remains a **separate, review-only** security change. It has not been applied. Even after its narrow five-function remediation, other PUBLIC functions and broad `service_role` tenant access must be inventoried before claiming database-enforced least privilege. Do not use a generic PostgreSQL login, generic SQL proxy, or `refresh` RPC to bridge this gap.

## Credential transport, if a Product-side broker is selected

No credential transport is implemented or authorized here. If the trusted comparator cannot be co-located with the approved Home Keychain source, a later design must use an owner-approved **private** network path, authenticated TLS 1.2+/1.3 with verified destination identity and preferably mutual client authentication, a single-use request tied to approval ID/device/enrollment/nonce/expiry, and an allowlisted Product-side receiver. Require no redirects, no proxy/body logging, no persistence or queueing of plaintext, bounded payload and timeout, encrypted memory where supported, and immediate disable/revocation. A public compare endpoint—even one hidden behind a bearer token—is out of scope. The Home credential must never be sent in this task. Verify transport cost and failure/rollback behavior before activation.

## Exact activation sequence (not authorized)

1. Security owner reviews the five writable functions, all inherited PUBLIC rights, all actual callers and Product-role compatibility. Approve a database-side privilege correction or a specifically risk-accepted broker isolation. No broad revocation by assumption.
2. Select an existing trusted private execution host; prove it has no new direct DB LOGIN, no public route, no generic SQL interface and no client-held service key. Review its ten-column/two-row read capability and destination identity. Any Production DDL, grant or deployment receives its own explicit authorization.
3. Verify the actual Gateway and Connector Keychain namespaces, exact pinned IDs and Production endpoint without reading tokens in logs or chat. Prove encrypted-at-rest approval/audit store, owner-only ACL, expiration, replay limit and revocation in the deployed host.
4. If transport is needed, approve and test the private authenticated-TLS path with synthetic credentials first. Authorize a separate bounded real-credential comparison window only after this gate.
5. Reconfirm each Production enrollment binding and current backup. Execute at most one approved comparison per device; do not invoke refresh/rotation. Record only status and redacted audit.
6. Disable the temporary executor/broker and revoke approval. Verify no route, process, credential copy, unintended query or extra cost remains. The camera telemetry transition, package installation, Keychain recovery rehearsal and live rollback are **separate later gates**.

**Rollback:** prior to Production activation, no rollback is needed. For a future private executor, revoke its approval and stop the private process first; remove only the newly deployed component. Do not alter existing device enrollment, token, source or QA identity. A Production ACL change, if separately authorized, needs a captured exact-ACL restore and a compatibility-verified rollback; regranting PUBLIC may reopen the known exposure. The existing 36-file configuration backup is preserved; live Keychain recovery remains limited and must not be called proven.

**Cost:** no new fixed supplier or Production resource was activated. A future bounded compare is expected to issue at most two exact-row reads per approval plus local audit entries, but any private transport/deployment cost is **unknown until selected** and must be checked against the supplier ledger and cost ceiling before activation.
