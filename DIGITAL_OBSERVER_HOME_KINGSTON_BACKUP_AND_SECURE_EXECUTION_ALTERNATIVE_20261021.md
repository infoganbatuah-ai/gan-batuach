## Consistent backup procedure — prepared, not executed

1. The owner selects an already approved physically independent destination with at least the measured capacity floor, encryption at rest, owner-only access, protected recovery key custody and enough separate restore space. Confirm the physical device/container identity; no supplier purchase or new paid plan is implied. Capture current source/destination free space, volume UUIDs and health, then define retention, RPO/RTO and manifest access. Stop if the destination is Kingston, insufficient, unencrypted, or ownership/security cannot be enforced.
2. Inventory present worktrees, each dirty/untracked/ignored set, stash and local-only commit against remote refs. Copy unique bytes only into an encrypted manifest-driven backup; do not stage, reset, clean, delete or change source files. Include local Development configuration and protected QA artifacts while excluding regenerable caches only with explicit evidence. Back up Git metadata/refs or independently verified bundles where required. Never put passwords, device credentials, private keys or media into Git.
3. Coordinate a bounded quiescence window for the **isolated Development** stack; do not touch installed Home Gateway/Connector. Confirm the exact Development environment and database identity. Use a consistent logical PostgreSQL snapshot with schema, data, Auth and migration history, plus role/extension/config inventory. Supabase Storage objects and bucket/policy metadata need separate capture; a `pg_dump` of metadata alone does not capture object bytes. Capture Colima VM/volume state or a tested reproducible rebuild path after a consistent shutdown. Avoid an online filesystem copy of a changing VM disk as purported database proof. Do not mix QA with Production credentials or assume the historical dump is current.
4. Record hashes, source SHA/version, file count, capture time, read-only encrypted destination identity and redacted manifest. Perform an isolated restore **off the live Kingston path**: restore a representative worktree and dirty file; start restored Development Postgres/Auth at a compatible migration point; verify representative tenant/Site rows and RLS; retrieve a private Storage object through its authorized policy; verify package integrity/config permissions. Measure restore duration and data gap. Never overwrite the live stack, installed services, Keychain or Production.
5. A failed/missing restore or missing data class keeps `BACKUP READINESS = BLOCKED`. Preserve existing backup archives and the detailed failure. Only a later successful independent restore allows a separate owner-approved disk-maintenance decision.

The Supabase-specific distinction between database/Auth state, Storage object bytes and RLS is mandatory for this backup plan; an exported SQL file by itself is not a full Product restore. The canonical `DIGITAL_OBSERVER_BACKUP_RESTORE_RUNBOOK.md` remains the Product contract.

## Alternative private execution without changing Kingston ownership

A **small FileVault-protected, ownership-enforcing internal runtime** is architecturally feasible, independent of a Kingston ownership toggle or a new sibling volume. Proposed bounded location (not created): an owner-only directory under `/Users/danielderi/Library/Application Support/Digital Observer/private-compare-runtime`. Keep ordinary source and build work on Kingston. Only an independently signed, sealed, hash-pinned one-shot **runtime copy** and minimal redacted approval state would cross to the protected internal location; never move the repository, Development DB, Xcode build storage, local device credentials or Production verifier there. The internal Data volume reports ownership enforcement and encryption, but its ~7.3 GiB free space is too small for backup; a reviewed runtime budget of at most 256 MiB must be measured and must retain OS headroom. No directory or package was installed.

This is **not a bypass of `noowners`**. The existing `home-legacy-kingston-executor.mjs` guard rightly rejects the current Kingston volume and pins source/artifacts to one external filesystem. It must stay fail-closed. A separate, reviewed internal-runtime guard would need to: authenticate the selected internal volume and owner-only path; verify the sealed package's trusted signature and pinned source digest before loading any code; forbid imports, symlinks, writable dependencies or fallback artifacts from the `noowners` checkout; recheck the runtime boundary before/after the one-shot comparison; keep Keychain reads within the existing host custody; and return only `UNKNOWN` on any boundary failure. The available Apple Development identity may help local signing after trust review, but no signed executor or owner-approved trust chain exists yet. An internal runtime is **FEASIBLE AS A DESIGN, NOT EXECUTION-READY**.

The independent audit receipt/sink, real Production administrator and revocation binding, two-enrollment database-side verifier restriction, authenticated private transport, Production deployment approval and live rollback remain separate blockers. A local protected directory grants none of those. Both real Home Legacy matches remain `UNKNOWN`; no Production comparison, camera restart, telemetry switch or PUSH 46 work is authorized. If these later security gates pass, the absent full Kingston backup and disk warnings should still be remediated for development-data protection, but a new Kingston APFS volume is **not** inherently required for a comparison executed entirely inside the protected internal boundary.
