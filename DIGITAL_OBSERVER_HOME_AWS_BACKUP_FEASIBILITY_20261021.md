### Selection controls

- **A — unique:** consistent Development Postgres state (including Auth and migration history), private Storage object bytes and metadata, unique local configuration, unpushed commits/stashes/dirty or ignored work, original signed artifacts, protected QA evidence and recovery manifests. Encrypt and include only after sensitivity review.
- **B — GitHub-reproducible:** verified pushed commits/refs and clean worktrees. Record remote SHA and restore procedure; do not assume dirty/ignored content is pushed.
- **C — rebuildable:** `node_modules`, DerivedData, Swift/build caches, redundant app bundles and VM caches *only after* proving the source and signed-package provenance are recoverable.
- **D — sensitive custody:** protected metadata/configuration requires owner-only encryption and access; macOS Keychain device credentials/private keys stay in Keychain. Never place secret values or Production credential verifiers in the backup manifest, Git or report.

## Candidate architecture — not activated

After account/resource verification, prefer a **separate private backup security boundary**, not an OTA-signing/release bucket. An existing S3 bucket is eligible only if bucket/prefix separation, policy, key custody, lifecycle, access logging and cost isolation are independently reviewed; do not infer suitability from mere existence. A dedicated bucket would itself be a new Production/account resource requiring separate approval. Block public access and ACLs, require TLS, enable versioning with explicit retention and noncurrent-version expiry, restrict writes to a backup-only principal and restore reads to an independently approved recovery principal, and require authenticated client-side encryption before upload plus S3 server-side encryption. Prefer SSE-S3 for the initial cost model; do **not** reuse OTA KMS signing keys. If a new customer-managed KMS key or Object Lock is legally/operationally required, price and approve it separately. Keep backup encryption/recovery keys in the approved secret custody, independent of the bucket; document loss risk and test key recovery without exporting Home Keychain items. Require object hashes, encrypted manifest, bounded object/request count, owner-only audit, lifecycle and deletion/hold review. Versioning and replication do not themselves prove recoverability.

For a later **isolated Development-only** consistent capture, confirm exact local database identity and coordinate a short quiescence/checkpoint window; take a transaction-consistent logical PostgreSQL dump of schema/data/Auth/migration history and role/extension/config inventory. Capture Supabase Storage bucket policies/metadata **and private object bytes separately**. Quiesce or consistently snapshot the Colima state only if a VM-level artifact is needed; do not call a live disk-image copy a valid database backup. Capture local Git deltas and protected QA originals under an encrypted manifest. Do not stop or query Production. No snapshot was taken in this audit.

Restore acceptance: in an isolated destination off the live Kingston path, verify manifest and object hashes, restore a representative dirty worktree and stash, start a compatible Development Postgres/Auth instance, verify migration history and representative tenant/Site/RLS denial, retrieve a private Storage object through authorized policy, validate signed-package provenance and config permissions, and measure RPO/RTO plus data gap. No restore was started; backup readiness remains **BLOCKED**.
